# Sources და Network Panel — ეტაპობრივი გაიდი

ამ პრაქტიკაში თქვენ იმუშავებთ API Dashboard აპლიკაციაზე, რომელიც JSONPlaceholder API-დან ტვირთავს მონაცემებს. ეს არის სპეციალურად შექმნილი სავარჯიშო, სადაც ისწავლით DevTools-ის ორ ძალიან მნიშვნელოვან პანელს — **Sources** (კოდის ნახვა, debugger, Snippets) და **Network** (ქსელური მოთხოვნების მონიტორინგი, throttling, HTTP სტატუს-კოდები).

პროექტი მდებარეობს `demo-sources-network/` ფოლდერში. ფაილები:

| ფაილი | აღწერა |
|-------|--------|
| `index.html` | API Dashboard-ის HTML — ღილაკები, ძებნა, კონტენტის არე, სურათი |
| `app.js` | JavaScript — API-დან მონაცემების ჩატვირთვა, ფილტრაცია, debugger statement |
| `styles.css` | სტილები — gradient header, ბარათები, spinner, responsive design |

---

## წინაპირობა: პროექტის გაშვება

```bash
cd ~/Desktop/Web-optimization/კვირა-3/ლექცია-3-sources-და-network-panel/demo-sources-network
npx serve -l 3000
```

გახსენით ბრაუზერში: `http://localhost:3000`

> **რატომ გვჭირდება სერვერი?** ჩვენი აპლიკაცია `fetch()` ფუნქციას იყენებს API-დან მონაცემების ჩასატვირთად. თუ HTML ფაილს პირდაპირ გახსნით (`file://` პროტოკოლით), ბრაუზერი fetch მოთხოვნებს დაბლოკავს CORS პოლიტიკის გამო. ლოკალური HTTP სერვერი (`http://localhost:3000`) ამ პრობლემას აგვარებს და, რაც მთავარია, Network panel-ში მოთხოვნები რეალისტურად გამოჩნდება.

## ეტაპი 1: Sources Panel — ფაილების ნახვა

### 1.1 Sources tab-ის გახსნა

1. გახსენით `http://localhost:3000`
2. DevTools გახსენით: **Cmd+Option+I** (Mac) ან **Ctrl+Shift+I** (Windows/Linux)
3. გადაერთეთ **Sources** tab-ზე

### 1.2 ფაილების ხე (File Tree)

Sources panel-ის მარცხენა მხარეს ხედავთ **Page** სექციას. გახსენით იგი:

```
Page
  └── top
      └── localhost:3000
          ├── index.html
          ├── app.js
          └── styles.css
```

ეს არის ყველა ფაილი, რომელიც ბრაუზერმა ჩატვირთა. **Page** სექცია აჩვენებს მიმდინარე გვერდის რესურსებს — HTML, JavaScript, CSS, სურათებს და ა.შ.

### 1.3 ფაილის გახსნა და კოდის ნახვა

1. დააჭირეთ **app.js**-ს ფაილების ხეში
2. მარჯვნივ გაიხსნება კოდის რედაქტორი

რას ხედავთ:
- **ხაზების ნომრები** — მარცხენა მხარეს (1, 2, 3...)
- **Syntax highlighting** — სხვადასხვა ელემენტი სხვადასხვა ფერითაა: string-ები, keyword-ები, ფუნქციის სახელები
- **გადახვევა** — ფაილი სრულად ჩანს, შეგიძლიათ გადახვიდეთ ნებისმიერ ხაზზე

### 1.4 ფაილში ძებნა

ფაილის შიგნით ტექსტის მოსაძებნად:

1. დააჭირეთ **Cmd+F** (Mac) ან **Ctrl+F** (Windows/Linux)
2. ჩაწერეთ `debugger`
3. ხაზი მონიშნულია — ხედავთ, რომ `debugger;` statement არის `loadData` ფუნქციაში

### 1.5 Quick Open — სწრაფი ნავიგაცია

1. დააჭირეთ **Cmd+P** (Mac) ან **Ctrl+P** (Windows/Linux)
2. გამოჩნდება ფაილების საძიებო ველი
3. ჩაწერეთ `app` — სიაში დაინახავთ `app.js`
4. დააჭირეთ Enter — ფაილი გაიხსნება

> **Quick Open** ძალიან სასარგებლოა, როცა პროექტში ბევრი ფაილია. ფაილის სახელის რამდენიმე ასოც საკმარისია მოსაძებნად.

## ეტაპი 2: debugger Statement

### 2.1 debugger-ის მოქმედება

ჩვენს `app.js` ფაილში `loadData` ფუნქციაში ჩაშენებულია `debugger;` statement. ეს არის სპეციალური JavaScript ბრძანება, რომელიც კოდის შესრულებას აჩერებს — თუ DevTools გახსნილია.

1. დარწმუნდით, რომ DevTools გახსნილია (**Sources** tab-ზე)
2. გვერდზე დააჭირეთ ღილაკს **„მომხმარებლების ჩატვირთვა"**
3. კოდის შესრულება გაჩერდება!

რას ხედავთ:
- გვერდზე **ლურჯი overlay** გამოჩნდება და ზემოთ ეწერება „Paused in debugger"
- Sources panel-ში `app.js` ფაილი ავტომატურად გაიხსნება
- `debugger;` ხაზი **ლურჯად** (ან ყვითლად) მონიშნულია — კოდი ზუსტად აქ გაჩერდა
- ფაილის ზემოთ ჩანს კონტროლის ღილაკები: Resume, Step Over, Step Into, Step Out

### 2.2 ცვლადების ინსპექტირება

კოდი გაჩერებულია — ეს ნიშნავს, რომ შეგიძლიათ ყველა ცვლადის მიმდინარე მნიშვნელობა ნახოთ:

**მაუსით hover:**
1. მაუსი მიიტანეთ `data` ცვლადზე კოდში — tooltip-ში დაინახავთ მასივს 10 ობიექტით
2. მაუსი მიიტანეთ `type` ცვლადზე — დაინახავთ `"users"`
3. მაუსი მიიტანეთ `response` ცვლადზე — დაინახავთ Response ობიექტს

**Scope panel (მარჯვნივ):**
1. მარჯვენა მხარეს ნახავთ **Scope** სექციას
2. **Local** — ლოკალური ცვლადები: `data`, `type`, `url`, `startTime`, `endTime`, `response`
3. **Closure** — closure-ში მოხვედრილი ცვლადები
4. **Global** — გლობალური ცვლადები: `window`, `document` და ა.შ.

**Watch panel:**
1. მარჯვნივ, Scope-ს ზემოთ, არის **Watch** სექცია
2. დააჭირეთ **+** ღილაკს
3. ჩაწერეთ `data.length` და დააჭირეთ Enter
4. დაინახავთ მნიშვნელობას: `10`
5. ჩაწერეთ `response.status` — დაინახავთ: `200`

### 2.3 Resume — შესრულების გაგრძელება

1. დააჭირეთ **F8** ან Resume ღილაკს (ლურჯი play ღილაკი ზემოთ)
2. კოდი გააგრძელებს შესრულებას
3. გვერდზე მომხმარებლების მონაცემები გამოჩნდება ბარათების სახით

> **მნიშვნელოვანი:** `debugger;` statement ყოველთვის წაშალეთ production კოდიდან! ის მხოლოდ დროებითი debugging-ის ინსტრუმენტია. თუ ვინმეს ბრაუზერში DevTools გახსნილი აქვს და თქვენს საიტზე `debugger;` ჩარჩა, კოდი გაუჩერდება — ეს ძალიან ცუდი გამოცდილებაა მომხმარებლისთვის.

## ეტაპი 3: Snippets — კოდის ფრაგმენტების შენახვა

### 3.1 Snippet-ის შექმნა

Snippets არის DevTools-ში ჩაშენებული მინი-რედაქტორი, სადაც JavaScript კოდის ფრაგმენტების შენახვა და გაშვება შეგიძლიათ.

1. Sources panel-ში, მარცხენა პანელის ზემოთ ნახავთ ორ tab-ს: **Page** და **Snippets**
2. დააჭირეთ **Snippets** tab-ს
3. დააჭირეთ **+ New snippet** ღილაკს
4. სახელად ჩაწერეთ `api-test`

### 3.2 კოდის დაწერა

Snippet-ის რედაქტორში ჩაწერეთ შემდეგი კოდი:

```javascript
fetch('https://jsonplaceholder.typicode.com/todos/1')
  .then(r => r.json())
  .then(data => {
    console.table(data);
    console.log('Title:', data.title);
  });
```

### 3.3 გაშვება

Snippet-ის გასაშვებად:
- დააჭირეთ **Cmd+Enter** (Mac) ან **Ctrl+Enter** (Windows/Linux)
- ან მარჯვენა ღილაკით დააჭირეთ snippet-ს და აირჩიეთ **Run**

**Console** tab-ზე გადასვლის შემდეგ დაინახავთ:

```
┌───────────┬───────────────────────────┐
│  (index)  │          Values           │
├───────────┼───────────────────────────┤
│  userId   │            1              │
│    id     │            1              │
│   title   │  'delectus aut autem'     │
│ completed │          false            │
└───────────┴───────────────────────────┘
Title: delectus aut autem
```

> **Snippets ინახება ბრაუზერში** — გვერდის refresh-ის შემდეგაც და სხვა საიტზე გადასვლის შემდეგაც ხელმისაწვდომია! ეს სასარგებლოა ხშირად გამოყენებული სატესტო სკრიპტების შესანახად.

## ეტაპი 4: Network Panel — მოთხოვნების მონიტორინგი

### 4.1 Network tab-ის გახსნა

1. DevTools-ში გადაერთეთ **Network** tab-ზე
2. ჩართეთ **Disable cache** checkbox (ზემოთ) — ეს აიძულებს ბრაუზერს ყოველი ფაილი თავიდან ჩატვირთოს
3. დარწმუნდით, რომ ჩაწერა ჩართულია — წითელი წრე (record ღილაკი) უნდა იყოს აქტიური
4. გააკეთეთ **Hard Refresh**: **Cmd+Shift+R** (Mac) ან **Ctrl+Shift+R** (Windows/Linux)

### 4.2 საწყისი მოთხოვნები

Refresh-ის შემდეგ Network panel-ში დაინახავთ გვერდის ჩატვირთვის ყველა მოთხოვნას:

| # | ფაილი | ტიპი | სტატუსი |
|---|-------|------|---------|
| 1 | `localhost` (ან `/`) | document | 200 |
| 2 | `styles.css` | stylesheet | 200 |
| 3 | `app.js` | script | 200 |
| 4 | `600/200` (picsum.photos) | image | 200 |

ქვემოთ, status bar-ში ჩანს ჯამური ინფორმაცია: რამდენი request, ჯამური ზომა, ჩატვირთვის დრო.

### 4.3 Request-ის დეტალური ინფორმაცია

დააჭირეთ **app.js** request-ს Network panel-ში. გაიხსნება დეტალური პანელი რამდენიმე tab-ით:

**Headers tab:**
- **Request URL:** `http://localhost:3000/app.js`
- **Request Method:** `GET`
- **Status Code:** `200 OK`
- **Content-Type:** `application/javascript; charset=UTF-8`

**Preview tab:**
- ფორმატირებული JavaScript კოდი — იგივე კოდი, რაც `app.js` ფაილშია

**Response tab:**
- Raw (დაუფორმატებელი) response — ზუსტად ის ბაიტები, რაც სერვერმა გამოგზავნა

**Timing tab:**
- მოთხოვნის ყოველი ფაზის დრო (ამას ეტაპ 8-ში დეტალურად განვიხილავთ)

### 4.4 API Request-ის ინსპექტირება

ახლა გავაკეთოთ რეალური API მოთხოვნა:

1. გვერდზე დააჭირეთ ღილაკს **„მომხმარებლების ჩატვირთვა"**
2. DevTools-ში `debugger` გააქტიურდება — დააჭირეთ **F8** (Resume) გასაგრძელებლად
3. Network panel-ში ახალი request გამოჩნდა: `users`

დააჭირეთ `users` request-ს და ნახეთ:

**Headers tab:**
- **Request URL:** `https://jsonplaceholder.typicode.com/users`
- **Request Method:** `GET`
- **Status Code:** `200 OK`
- **Content-Type:** `application/json; charset=utf-8`

**Preview tab:**
- ფორმატირებული JSON — მასივი მომხმარებლების ობიექტებით. თითოეულ ობიექტს აქვს `name`, `email`, `address`, `company` და ა.შ.

**Response tab:**
- Raw JSON string — ლამაზად ფორმატირებული Preview-სგან განსხვავებით, აქ ზუსტად ის ტექსტია, რაც სერვერმა დააბრუნა

> **Headers tab-ში** ორი სექციაა: **Response Headers** (რა გამოგზავნა სერვერმა — Content-Type, Cache-Control და ა.შ.) და **Request Headers** (რა გაგზავნა ბრაუზერმა — Accept, User-Agent და ა.შ.). ეს ინფორმაცია აუცილებელია debugging-ისთვის, როცა API არ მუშაობს მოსალოდნელად.

## ეტაპი 5: Network ფილტრები

### 5.1 ფილტრის ტიპები

Network panel-ის ზემოთ არის ფილტრების ზოლი. ეს ღილაკები აფილტრებს request-ებს ტიპის მიხედვით:

| ფილტრი | რას აჩვენებს |
|--------|-------------|
| **All** | ყველა მოთხოვნა |
| **Fetch/XHR** | API calls — `fetch()` და `XMLHttpRequest` მოთხოვნები |
| **JS** | JavaScript ფაილები |
| **CSS** | CSS ფაილები |
| **Img** | სურათები (PNG, JPG, WebP, SVG...) |
| **Font** | შრიფტის ფაილები |
| **Doc** | HTML დოკუმენტები |
| **WS** | WebSocket კავშირები |
| **Media** | აუდიო/ვიდეო ფაილები |

**სცადეთ:**

1. პირველ რიგში, ჩატვირთეთ მონაცემები — დააჭირეთ **„მომხმარებლების ჩატვირთვა"** და **„პოსტების ჩატვირთვა"** (debugger-ზე F8 დააჭირეთ)
2. დააჭირეთ **Fetch/XHR** ფილტრს — მხოლოდ API request-ები ჩანს (`users`, `posts`)
3. დააჭირეთ **JS** — მხოლოდ `app.js` ჩანს
4. დააჭირეთ **CSS** — მხოლოდ `styles.css` ჩანს
5. დააჭირეთ **Img** — მხოლოდ picsum.photos-ის სურათი ჩანს
6. დააჭირეთ **All** — ყველა request-ი ისევ ჩანს

### 5.2 ტექსტური ფილტრი

ფილტრების ზოლის მარცხენა მხარეს არის ტექსტური საძიებო ველი:

1. ჩაწერეთ `users` — მხოლოდ users request ჩანს
2. წაშალეთ და ჩაწერეთ `css` — styles.css გამოჩნდება
3. წაშალეთ ტექსტი — ყველა request ისევ ჩანს

> ტექსტური ფილტრი URL-ში ეძებს. თუ API-ს ბევრი endpoint-ი გაქვთ, ეს ძალიან სასარგებლო ინსტრუმენტია კონკრეტული request-ის სწრაფად მოსაძებნად.

### 5.3 Waterfall — ჩატვირთვის თანმიმდევრობა

Network panel-ის მარჯვენა მხარეს ჩანს **Waterfall** სვეტი — ჰორიზონტალური ზოლები, რომლებიც აჩვენებს, როდის დაიწყო და რამდენ ხანს გაგრძელდა თითოეული request.

რას შეამჩნევთ:
- **index.html** პირველი ჩაიტვირთება — ის არის საწყისი დოკუმენტი
- **styles.css** და **app.js** თითქმის ერთდროულად იწყება — ბრაუზერმა HTML-ში ორივე ლინკი იპოვა და პარალელურად ტვირთავს
- **სურათი** (picsum.photos) ოდნავ მოგვიანებით იწყება — ის HTML-ის `<img>` ელემენტიდან ჩაიტვირთება, მას შემდეგ რაც ბრაუზერი იმ ხაზს მიაღწევს
- **API request-ები** (users, posts) მხოლოდ ღილაკზე დაჭერის შემდეგ ჩნდება

## ეტაპი 6: Throttling — ქსელის შენელება

### 6.1 Slow 3G სიმულაცია

Throttling საშუალებას გაძლევთ სიმულაცია გაუკეთოთ ნელ ქსელურ კავშირს. ეს აუცილებელია იმის შესამოწმებლად, როგორ იქცევა თქვენი აპლიკაცია მობილურ ინტერნეტზე.

1. Network tab-ზე, ზემოთ ნახავთ dropdown-ს, სადაც ეწერება **No throttling**
2. დააჭირეთ და აირჩიეთ **Slow 3G**
3. გვერდზე დააჭირეთ **„პოსტების ჩატვირთვა"** (F8 — debugger-ზე Resume)
4. დააკვირდით — loading spinner ბევრად დიდხანს ტრიალებს!

### 6.2 შედარება

სცადეთ იგივე request ჩვეულებრივ და Slow 3G-ზე. დაინახავთ რადიკალურ განსხვავებას:

| პარამეტრი | No Throttling | Slow 3G |
|-----------|---------------|---------|
| TTFB (Time To First Byte) | ~100-300ms | ~2000ms+ |
| Content Download | ~10-50ms | ~500-2000ms |
| სულ დრო | ~150-400ms | ~2500-4000ms |
| მომხმარებლის განცდა | მყისიერი | შესამჩნევი ლოდინი |

> რიცხვები დამოკიდებულია თქვენი ინტერნეტის სიჩქარეზე, მაგრამ პროპორცია ყოველთვის მსგავსია — Slow 3G-ზე 5-10-ჯერ ნელია.

### 6.3 Offline რეჟიმი

1. Throttling dropdown-ში აირჩიეთ **Offline**
2. დააჭირეთ **„კომენტარების ჩატვირთვა"**
3. Network panel-ში ხედავთ: request **წითლად** მონიშნულია, სტატუსი `(failed)`
4. Console-ში ჩანს შეცდომა:

```
შეცდომა: Failed to fetch
```

5. გვერდზე ჩანს შეცდომის შეტყობინება

ეს სიმულაცია გვიჩვენებს, რა ხდება, როცა მომხმარებელს ინტერნეტი ეწყდება. კარგი აპლიკაცია ასეთ სიტუაციას გამართულად უმკლავდება — შეცდომის შეტყობინებით, retry ღილაკით, ან ოფლაინ რეჟიმით.

> **ყოველთვის დააბრუნეთ "No throttling"** ტესტირების შემდეგ! თუ დაგავიწყდებათ, ყველა საიტი გაუგებრად ნელა იმუშავებს და დაგაბნევთ.

## ეტაპი 7: HTTP Status Codes — 404 შეცდომა

### 7.1 404 request-ის გამოწვევა

ჩვენს აპლიკაციაში სპეციალურად არის ღილაკი, რომელიც არასწორ URL-ს მიმართავს:

1. Throttling დააბრუნეთ **No throttling**-ზე
2. გვერდზე დააჭირეთ **„არასწორი URL (404)"**
3. Network panel-ში ახალი request ჩნდება — **წითელი ფერით** მონიშნული
4. სტატუსი: **404**

### 7.2 Headers-ის ინსპექტირება

დააჭირეთ ამ წითელ request-ს Network panel-ში:

**Headers tab:**
- **Request URL:** `https://jsonplaceholder.typicode.com/nonexistent-endpoint`
- **Request Method:** `GET`
- **Status Code:** `404 Not Found`

Console-ში ასევე ჩანს:
```
Response status: 404
Response ok: false
404 შეცდომა: HTTP 404 — Not Found
```

### 7.3 HTTP Status Codes ცხრილი

HTTP სტატუს-კოდები სერვერის პასუხის სტანდარტული კოდებია. ყველა web developer-მა უნდა იცოდეს ძირითადი კოდები:

| კოდი | სახელი | აღწერა |
|------|--------|--------|
| **200** | OK | წარმატებული request — სერვერმა მონაცემები დააბრუნა |
| **201** | Created | ახალი რესურსი შეიქმნა (მაგ., POST request-ის შემდეგ) |
| **301** | Moved Permanently | რესურსი სხვა URL-ზე გადავიდა სამუდამოდ |
| **400** | Bad Request | request არასწორია — სერვერმა ვერ გაიგო, რა გინდოდა |
| **401** | Unauthorized | ავტორიზაცია საჭიროა — შედით სისტემაში |
| **403** | Forbidden | აკრძალულია — შესული ხართ, მაგრამ ეს რესურსი არ გეკუთვნით |
| **404** | Not Found | რესურსი ვერ მოიძებნა — URL არასწორია ან რესურსი აღარ არსებობს |
| **500** | Internal Server Error | სერვერის შიდა შეცდომა — სერვერზე რაღაც გატყდა |

> **401 vs 403:** ეს ორი ხშირად ერევათ ერთმანეთში. **401** ნიშნავს „ვინ ხარ? დამიმტკიცე" (არ ხარ შესული). **403** ნიშნავს „ვიცი ვინ ხარ, მაგრამ არ გაქვს უფლება" (შესული ხარ, მაგრამ წვდომა არ გაქვს).

## ეტაპი 8: Timing Breakdown — მოთხოვნის ფაზები

### 8.1 Timing tab-ის კითხვა

ყოველ ქსელურ მოთხოვნას აქვს რამდენიმე ფაზა. ეს ინფორმაცია კრიტიკულად მნიშვნელოვანია performance optimization-ისთვის.

1. დააჭირეთ **„მომხმარებლების ჩატვირთვა"** (F8 — debugger-ზე Resume)
2. Network panel-ში დააჭირეთ `users` request-ს
3. გახსენით **Timing** tab

დაინახავთ ჰორიზონტალურ ზოლებს, რომლებიც აჩვენებს თითოეული ფაზის ხანგრძლივობას:

| ფაზა | აღწერა |
|------|--------|
| **Queueing** | რიგში დგომა — ბრაუზერი ელოდება, სანამ ადგილი გამოთავისუფლდება (ბრაუზერი ერთდროულად 6 კავშირს ხსნის ერთ domain-ზე) |
| **Stalled** | ბლოკირება — request მზადაა, მაგრამ ჯერ ვერ იგზავნება (proxy-ს ელოდება, ან კავშირი მზადდება) |
| **DNS Lookup** | დომენის IP მისამართად გარდაქმნა — `jsonplaceholder.typicode.com` → `104.21.x.x` |
| **Initial Connection** | TCP კავშირის დამყარება — ბრაუზერი და სერვერი „ხელს ართმევენ ერთმანეთს" |
| **SSL** | HTTPS handshake — დაშიფრული კავშირის დამყარება (მხოლოდ HTTPS-ისთვის) |
| **TTFB** | Time To First Byte — დრო request-ის გაგზავნიდან პირველი ბაიტის მიღებამდე. ეს არის სერვერის „ფიქრის დრო" |
| **Content Download** | კონტენტის ჩამოტვირთვა — რამდენ ხანს ტვირთავს ბრაუზერი response-ის სხეულს |

### 8.2 TTFB-ის მნიშვნელობა

**TTFB (Time To First Byte)** არის ყველაზე მნიშვნელოვანი მეტრიკა Timing tab-ში. ის გვიჩვენებს:
- რამდენი ხანი სჭირდება სერვერს request-ის დამუშავება
- ქსელის latency-ს (მოგზაურობის დრო ბრაუზერიდან სერვერამდე და უკან)

**შედარება — სცადეთ:**

1. დააჭირეთ **„მომხმარებლების ჩატვირთვა"** — Timing tab-ში ჩაინიშნეთ TTFB
2. დააჭირეთ **„პოსტების ჩატვირთვა"** — ჩაინიშნეთ TTFB
3. დააჭირეთ **„კომენტარების ჩატვირთვა"** — ჩაინიშნეთ TTFB

შეამჩნევთ:
- პირველ request-ს DNS Lookup და Initial Connection აქვს (პირველად უკავშირდება სერვერს)
- მეორე და მესამე request-ში ეს ფაზები **0ms** ან ძალიან მცირეა — ბრაუზერმა კავშირი შეინარჩუნა (keep-alive)
- TTFB სხვადასხვა request-ისთვის შეიძლება განსხვავდებოდეს — ეს სერვერის დატვირთვაზე და მონაცემების ზომაზე დამოკიდებულია

### 8.3 Slow 3G-ზე Timing-ის შედარება

1. Throttling-ში აირჩიეთ **Slow 3G**
2. დააჭირეთ **„მომხმარებლების ჩატვირთვა"** (F8 — Resume)
3. Timing tab-ში ნახავთ: TTFB დრამატიულად გაიზარდა, Content Download-იც გაგრძელდა

> **როცა აპლიკაცია ნელია, Timing tab გეუბნებათ — ვის აქვს ბრალი.** თუ TTFB დიდია — სერვერი ნელია ან ქსელი შეფერხებულია. თუ Content Download დიდია — response ძალიან დიდი ზომისაა და კომპრესია ან pagination სჭირდება.

**არ დაგავიწყდეთ:** დააბრუნეთ **No throttling**!

## შეჯამება

ამ პრაქტიკაში ჩვენ ვისწავლეთ DevTools-ის ორი ძლიერი პანელი. აი, რა შეგვიძლია ახლა:

| ინსტრუმენტი | რისთვის ვიყენებთ |
|-------------|------------------|
| **Sources > File Tree** | პროექტის ფაილების ნახვა, კოდის წაკითხვა |
| **Sources > Quick Open (Cmd+P)** | ფაილის სწრაფი მოძებნა სახელით |
| **Sources > Cmd+F** | კოდში ტექსტის ძებნა |
| **debugger statement** | კოდის შეჩერება კონკრეტულ ხაზზე |
| **Scope / Watch panels** | ცვლადების მიმდინარე მნიშვნელობების ნახვა |
| **Snippets** | JavaScript ფრაგმენტების შენახვა და გაშვება |
| **Network > Request list** | ყველა ქსელური მოთხოვნის მონიტორინგი |
| **Network > Headers** | Request/Response headers-ის ინსპექტირება |
| **Network > Preview/Response** | სერვერის პასუხის ნახვა |
| **Network > Timing** | მოთხოვნის თითოეული ფაზის დროის ანალიზი |
| **Network > Filters** | request-ების ფილტრაცია ტიპით (XHR, JS, CSS, Img) |
| **Network > Waterfall** | ჩატვირთვის თანმიმდევრობისა და პარალელიზმის ვიზუალიზაცია |
| **Throttling** | ნელი ქსელის სიმულაცია (Slow 3G, Fast 3G, Offline) |
| **HTTP Status Codes** | სერვერის პასუხის სტატუსის გაგება (200, 404, 500...) |

### მთავარი წესები

1. **Sources Panel** — თქვენი კოდის „რენტგენი". აქ ხედავთ ზუსტად იმ კოდს, რასაც ბრაუზერი ასრულებს, შეგიძლიათ breakpoint-ების დასმა და ცვლადების ინსპექტირება.
2. **debugger statement** — სწრაფი გზა კოდის შესაჩერებლად, მაგრამ ყოველთვის წაშალეთ production-იდან.
3. **Network Panel** — ყველა ქსელური მოთხოვნის დეტექტივი. Headers, Preview, Response და Timing tab-ები სრულ სურათს გაძლევენ.
4. **Throttling** — ყოველთვის შეამოწმეთ აპლიკაცია ნელ ქსელზე. თქვენი სწრაფი Wi-Fi არ ნიშნავს, რომ მომხმარებელსაც სწრაფი კავშირი აქვს.
5. **HTTP Status Codes** — ისწავლეთ ძირითადი კოდები (200, 400, 401, 403, 404, 500). Network panel-ში ისინი პირველი რამაა, რასაც ნახავთ — სწორი სტატუსი ნიშნავს, რომ სერვერი მუშაობს; არასწორი — პრობლემის ტიპს მიუთითებს.
