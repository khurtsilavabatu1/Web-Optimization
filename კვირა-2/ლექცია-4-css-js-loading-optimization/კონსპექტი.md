# ლექცია 4 — CSS/JS ჩატვირთვის ოპტიმიზაცია + პრაქტიკა

## 4.1 Critical CSS

### რატომ არის მნიშვნელოვანი?
- ბრაუზერი HTML-ს ზემოდან ქვემოთ კითხულობს. როცა `<link rel="stylesheet">` ტეგს ხვდება, **ჩერდება** — CSS ფაილს ჩამოტვირთავს, დაამუშავებს და მხოლოდ ამის შემდეგ აგრძელებს გვერდის ხატვას. ამას ეწოდება **render-blocking**.
- თუ CSS ფაილი დიდია (მაგ. 200KB), მომხმარებელი თეთრ ეკრანს ხედავს სანამ მთლიანი ფაილი ჩაიტვირთება — იმ სტილებითაც, რომლებიც ეკრანის ქვედა ნაწილს ეხება და ახლა საერთოდ არ ჩანს.

> **Critical CSS** — ის მინიმალური CSS, რომელიც საჭიროა მომხმარებლის ეკრანზე ხილული ნაწილის (above-the-fold) გამოსახატად. ამ სტილებს პირდაპირ HTML-ში ჩავწერთ `<style>` ტეგით, რომ ბრაუზერმა ცალკე ფაილის ჩამოტვირთვა არ დასჭირდეს. დანარჩენი CSS ასინქრონულად იტვირთება — გვერდი მაშინვე გამოჩნდება და სტილები ფონში დაემატება.
>
> **Above-the-fold** — ეკრანზე ხილული ნაწილი სანამ მომხმარებელი დასქროლავს. ტერმინი გაზეთის ინდუსტრიიდან მოდის — გაზეთი ნახევრად იყო დაკეცილი და მნიშვნელოვანი სათაურები "ნაკეცის ზემოთ" თავსდებოდა.

```html
<head>
  <!-- Critical CSS inline — above-the-fold სტილები პირდაპირ HTML-ში -->
  <style>
    .header { display: flex; padding: 16px; }
    .hero { height: 100vh; background: #f5f5f5; }
  </style>
  
  <!-- დანარჩენი CSS ასინქრონულად -->
  <link rel="preload" href="styles.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="styles.css"></noscript>
</head>
```

> **როგორ მუშაობს ასინქრონული CSS ჩატვირთვა ზემოთ?** `<link rel="preload" as="style">` ბრაუზერს ეუბნება: "ეს ფაილი ჩამოტვირთე, მაგრამ ჯერ არ გამოიყენო როგორც სტილი". `onload`-ით — ჩამოტვირთვის შემდეგ `rel`-ს ვუცვლით `stylesheet`-ზე და მაშინ ბრაუზერი სტილებს გამოიყენებს. `this.onload=null` ხელმეორე გამოძახებას ბლოკავს. `<noscript>` fallback-ია იმ შემთხვევისთვის თუ JavaScript გამორთულია — მაშინ CSS ჩვეულებრივად ჩაიტვირთება.
>
> **როგორ ამოვიცნოთ Critical CSS?** ხელით არ უნდა ამოწერო — არსებობს ინსტრუმენტები: **Critical** (npm პაკეტი), **Critters** (Webpack/Vite plugin). ეს ინსტრუმენტები ბრაუზერს "ხსნიან" გვერდს, უყურებენ რა ჩანს ეკრანზე, და იმ CSS-ს ავტომატურად ამოიღებენ.

## 4.2 Script Loading Strategies

### რატომ არის მნიშვნელოვანი?
- JavaScript-ის ჩატვირთვა და შესრულება ნაგულისხმევად **ბლოკავს** HTML-ის დამუშავებას — ბრაუზერი ჩერდება, ელოდება ფაილის ჩამოტვირთვას და შესრულებას, და მხოლოდ შემდეგ აგრძელებს HTML-ის კითხვას.
- დიდ აპლიკაციებში შეიძლება რამდენიმე JS ფაილი იყოს — თუ ყველა ნაგულისხმევ რეჟიმში ჩაიტვირთება, გვერდი სერიოზულად შენელდება.

> **HTML Parsing** — პროცესი, როცა ბრაუზერი HTML კოდს კითხულობს და DOM ხეს (დოკუმენტის სტრუქტურას) აგებს. `<script>` ტეგი ამ პროცესს აჩერებს, რადგან JavaScript-ს შეუძლია DOM-ის შეცვლა (მაგ. `document.write()`) და ბრაუზერი ელოდება, სანამ სკრიპტი დაამთავრებს მუშაობას.

```html
<!-- Default — ბლოკავს HTML parsing-ს -->
<script src="app.js"></script>

<!-- async — ჩატვირთავს პარალელურად, შეასრულებს მაშინვე -->
<script src="analytics.js" async></script>

<!-- defer — ჩატვირთავს პარალელურად, შეასრულებს HTML parsing-ის შემდეგ -->
<script src="app.js" defer></script>
```

```
HTML:    ████████████████████████████████
default: ----████████--(blocked)--███████
async:   ----████████----███████---------
defer:   ----████████-----------███████--
                ↑load     ↑execute
```

> **დიაგრამის ახსნა:** ზედა ხაზი (HTML) არის ბრაუზერის HTML parsing-ის პროცესი. თითოეული ვარიანტისთვის ნაჩვენებია ორი ფაზა: **load** (ფაილის ჩამოტვირთვა) და **execute** (კოდის შესრულება).
>
> - **default** — ბრაუზერი ჩერდება, ჩამოტვირთავს ფაილს, შეასრულებს და მხოლოდ მერე აგრძელებს HTML-ს. ამიტომაა `(blocked)` — ეკრანზე ჯერ არაფერი ჩნდება ამ დროს.
> - **async** — ფაილის ჩამოტვირთვა HTML-ის პარალელურად მიმდინარეობს (არ ბლოკავს). მაგრამ როცა ჩამოტვირთვა დამთავრდება, **მაშინვე** შეასრულებს — HTML parsing შეჩერდება შესრულების დროს. მნიშვნელოვანია: **თანმიმდევრობა არ არის გარანტირებული** — რომელი ფაილიც პირველი ჩაიტვირთება, პირველი შესრულდება.
> - **defer** — ჩამოტვირთვა ასევე პარალელურია, მაგრამ შესრულება **მხოლოდ HTML parsing-ის დასრულების შემდეგ** ხდება. თანმიმდევრობა **გარანტირებულია** — `defer` სკრიპტები იმ მიმდევრობით სრულდება, რა მიმდევრობითაც HTML-ში წერია.

### რომელი როდის გამოვიყენოთ?

- **`defer`** — აპლიკაციის მთავარი სკრიპტებისთვის (`app.js`, `main.js`). DOM-ზე დამოკიდებულია, თანმიმდევრობა მნიშვნელოვანია — **ყველაზე ხშირად რეკომენდებული**
- **`async`** — დამოუკიდებელი სკრიპტებისთვის, რომლებსაც სხვა სკრიპტებთან არანაირი კავშირი არ აქვთ — analytics, ads, tracking pixels
- **default (არაფერი)** — თითქმის არასდროს. მხოლოდ თუ სკრიპტმა ზუსტად იმ ადგილას უნდა იმუშაოს (ძალიან იშვიათი)

## 4.3 Resource Hints

### რატომ არის მნიშვნელოვანი?
- ბრაუზერი HTML-ს ზემოდან ქვემოთ კითხულობს და რესურსებს მაშინ ტვირთავს, როცა ხვდება მათ. Resource hints-ით ბრაუზერს **წინასწარ ვაფრთხილებთ** რომ მალე რაღაც დასჭირდება — ამან შეიძლება ასეულ მილიწამებს დაზოგოს.

> **რესურსის ჩატვირთვა რამდენიმე ეტაპისგან შედგება:** DNS Lookup (დომენის IP მისამართის პოვნა) → TCP Connection (კავშირის დამყარება) → TLS Handshake (დაშიფვრის მოლაპარაკება, HTTPS-ისთვის) → Request/Response (ფაილის მოთხოვნა და მიღება). Resource hints-ით ამ ეტაპებს წინასწარ ვასრულებთ, რესურსი რომ საჭირო გახდება, უკვე მზად იყოს.

```html
<head>
  <!-- DNS Prefetch — დომენის resolve წინასწარ -->
  <link rel="dns-prefetch" href="https://api.example.com">
  
  <!-- Preconnect — TCP + TLS კავშირი წინასწარ -->
  <link rel="preconnect" href="https://fonts.googleapis.com">
  
  <!-- Prefetch — შემდეგი გვერდის რესურსი -->
  <link rel="prefetch" href="/next-page.js">
  
  <!-- Preload — კრიტიკული რესურსი ახლავე -->
  <link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin>
</head>
```

> **`dns-prefetch`** — ყველაზე მსუბუქი hint. მხოლოდ DNS lookup-ს აკეთებს წინასწარ (დომენის სახელს IP მისამართად გარდაქმნის). სასარგებლოა, როცა იცი რომ მომხმარებელი მალე სხვა დომენის რესურსს მოითხოვს. ფასი თითქმის ნულოვანია — 0-5ms CPU, რამდენიმე ბაიტი მეხსიერება.
>
> **`preconnect`** — dns-prefetch-ზე ერთი ნაბიჯით მეტი: DNS + TCP + TLS სრულად. დაზოგავს 100-300ms. გამოიყენე მხოლოდ კრიტიკული third-party დომენებისთვის (მაგ. Google Fonts, CDN). ზედმეტი preconnect-ები CPU-ს ხარჯავს ტყუილად, ამიტომ 2-3 დომენზე მეტზე არ არის რეკომენდებული.
>
> **`prefetch`** — მთლიანი ფაილის ჩამოტვირთვა **ძალიან დაბალ პრიორიტეტზე**. ფაილს ქეშში ინახავს, რომ შემდეგ გვერდზე გადასვლისას მაშინვე მზად იყოს. მაგალითად: საწყისი გვერდიდან პროდუქტის გვერდის JS-ის prefetch — მომხმარებელი რომ პროდუქტზე დააკლიკებს, სკრიპტი უკვე ჩამოტვირთული ექნება.
>
> **`preload`** — ბრაუზერს ეუბნები: "ეს რესურსი **ახლავე** სჭირდება ამ გვერდს, მაქსიმალურ პრიორიტეტზე ჩამოტვირთე". განსხვავებით prefetch-ისგან, preload **მიმდინარე** გვერდისთვისაა, არა მომავლისთვის. გამოიყენე ფონტებისთვის, hero image-ისთვის, critical CSS/JS-ისთვის.
>
> **`crossorigin`** ატრიბუტი preload-ზე ფონტებისთვის **სავალდებულოა**, თუნდაც ფონტი შენს სერვერზე იყოს. ფონტები CORS მოთხოვნით იტვირთება და `crossorigin`-ის გარეშე ბრაუზერი ფონტს ორჯერ ჩამოტვირთავს — ერთხელ preload-ით, ერთხელ `@font-face`-ით.

### შეჯამების ცხრილი:

- **dns-prefetch** — როდის: მალე დაგჭირდება სხვა დომენის რესურსი, რისთვის: მხოლოდ DNS resolve, ფასი: მინიმალური
- **preconnect** — როდის: მალე დაგჭირდება სხვა დომენის რესურსი, რისთვის: DNS + TCP + TLS, ფასი: საშუალო (2-3 დომენამდე)
- **prefetch** — როდის: შემდეგ გვერდზე დასჭირდება, რისთვის: ნავიგაციის დაჩქარება, ფასი: ტრაფიკი (დაბალი პრიორიტეტი)
- **preload** — როდის: ახლავე სჭირდება ამ გვერდს, რისთვის: ფონტი, hero image, critical resource, ფასი: მაღალი პრიორიტეტი

## 4.4 CSS მიწოდების ოპტიმიზაცია

### რატომ არის მნიშვნელოვანი?
- ყოველი CSS ფაილი ნაგულისხმევად **render-blocking**-ია — ბრაუზერი არ დახატავს არაფერს, სანამ ყველა CSS ფაილს არ ჩამოტვირთავს და არ დაამუშავებს.
- თუ ერთ დიდ ფაილში ყველა სტილი გაქვს (print სტილები, desktop-only სტილები, ანიმაციები), მომხმარებელი ყველაფრის ჩატვირთვას ელოდება, თუნდაც მისი მოწყობილობისთვის ნახევარი არ სჭირდებოდეს.

```html
<!-- Render-blocking (default) -->
<link rel="stylesheet" href="all-styles.css">

<!-- Media query — ჩატვირთავს, მაგრამ არ დაბლოკავს -->
<link rel="stylesheet" href="print.css" media="print">
<link rel="stylesheet" href="desktop.css" media="(min-width: 1024px)">
```

> **როგორ მუშაობს media ატრიბუტი?** ბრაუზერი CSS ფაილს ორივე შემთხვევაში ჩამოტვირთავს, მაგრამ `media` ატრიბუტით ეუბნები: "ეს ფაილი მხოლოდ ამ პირობისთვისაა". თუ პირობა არ სრულდება (მაგ. `media="print"` მაშინ, როცა ეკრანზე იყურება), ბრაუზერი ამ ფაილს **არ მიიჩნევს render-blocking-ად** და გვერდის ხატვას არ დააყოვნებს. ფაილი ფონში ჩაიტვირთება — print-ზე გადასვლისას ან ეკრანის ზომის შეცვლისას მზად იქნება.
>
> **პრაქტიკული რჩევა:** თუ პროექტში ერთი დიდი CSS ფაილი გაქვს, დაყავი: critical სტილები inline `<style>`-ში (იხ. 4.1), print სტილები ცალკე ფაილში `media="print"`-ით, და მოწყობილობის ზომის მიხედვით — `media="(min-width: 1024px)"`. ეს არ ამცირებს მთლიან ჩამოტვირთულ მოცულობას, მაგრამ გვერდი **ადრე გამოჩნდება**.

### გამოუყენებელი CSS-ის პოვნა:
```
Chrome DevTools → Cmd+Shift+P → "Coverage" → Start
წითელი = გამოუყენებელი კოდი
```

> **Coverage tool** აჩვენებს თითოეული CSS (და JS) ფაილიდან რამდენი პროცენტი რეალურად გამოიყენება მიმდინარე გვერდზე. წითლად მონიშნული ხაზები არასდროს შესრულდა / გამოყენებულ იქნა. თუ CSS ფაილის 70% წითელია — ანუ მომხმარებელი 70%-ს ტყუილად ტვირთავს. ეს არ ნიშნავს რომ მაშინვე უნდა წაშალო — შეიძლება სხვა გვერდზე სჭირდებოდეს. მაგრამ ეს მონაცემები გვეხმარება გავიგოთ, სად არის ოპტიმიზაციის პოტენციალი.
>
> **PurgeCSS / UnCSS** — build-ის დროს გაშვებადი ინსტრუმენტები, რომლებიც ავტომატურად შლიან გამოუყენებელ CSS-ს. Tailwind CSS-ს ეს ჩაშენებული აქვს — production build-ში მხოლოდ იმ კლასებს ტოვებს, რომლებიც რეალურად HTML/JSX-ში გამოიყენება.

## 4.5 Bundle Analysis

### რატომ არის მნიშვნელოვანი?
- თანამედროვე პროექტებში `npm install`-ით ბევრ პაკეტს ვამატებთ. თითოეული პაკეტი საბოლოო bundle-ში ხვდება, რომელსაც მომხმარებელი ჩამოტვირთავს.
- ხშირად ერთი პატარა ფუნქციისთვის მთლიანი დიდი ბიბლიოთეკა იტვირთება (მაგ. `lodash`-ის მხოლოდ `_.get()`-ს იყენებ, მაგრამ 70KB სრულ ბიბლიოთეკას ტვირთავ).

> **Bundle** — საბოლოო JavaScript ფაილი (ან ფაილები), რომელსაც build tool (Vite, Webpack) აწყობს შენი source კოდიდან და ყველა dependency-დან. ეს ფაილი მომხმარებელს ჩამოტვირთავს. რაც უფრო დიდია bundle, მით მეტ დროს ხარჯავს მომხმარებელი ჩამოტვირთვაზე და ბრაუზერი — კოდის parsing-ზე/შესრულებაზე.
>
> **Bundle analyzer** — ვიზუალური ინსტრუმენტი, რომელიც bundle-ის შემადგენლობას ბლოკების სახით აჩვენებს. ბლოკის ზომა პროპორციულია ფაილის ზომისა. ეს მაშინვე გვიჩვენებს, რომელი ბიბლიოთეკა იკავებს ყველაზე მეტ ადგილს და სად ღირს ოპტიმიზაცია.

```bash
# Vite
npx vite-bundle-visualizer

# Webpack
npx webpack-bundle-analyzer dist/stats.json
```

> **ტიპიური აღმოჩენები bundle analyzer-ით:**
> - `moment.js` — 300KB+ (ყველა locale-ით), შეცვალე `date-fns`-ით (~5KB საჭირო ფუნქციებისთვის) ან `dayjs`-ით (~2KB)
> - `lodash` — 70KB (სრული), შეცვალე `lodash-es`-ით და მხოლოდ საჭიროს იმპორტირე: `import get from 'lodash-es/get'`
> - დუბლიკატი პაკეტები — ერთი და იგივე ბიბლიოთეკის სხვადასხვა ვერსია bundle-ში ორჯერ ხვდება
>
> **Tree Shaking** — build tool-ის (Vite/Webpack) უნარი, ამოიღოს კოდიდან ის ფუნქციები/მოდულები, რომლებიც არსად გამოიყენება. მუშაობს მხოლოდ ES Modules-თან (`import/export`). ამიტომაა `lodash-es` უკეთესი ვიდრე `lodash` — ES Modules ფორმატშია და build tool-ს შეუძლია გამოუყენებული ფუნქციები ამოაგდოს.
