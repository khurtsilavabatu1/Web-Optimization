# ლექცია 2 — მინიმიზაცია და კომპრესია

## 2.1 რესურსების მინიმიზაცია (Minification)

### რა არის?
Minification — კოდიდან ზედმეტი სიმბოლოების მოშორება (spaces, comments, long variable names) ფუნქციონალურობის შეცვლის გარეშე.

### JavaScript Minification:
```javascript
// წყარო (1.2KB)
function calculateTotalPrice(items, taxRate) {
  // გამოვთვალოთ ჯამური ფასი
  let total = 0;
  for (let i = 0; i < items.length; i++) {
    const item = items[i];
    total += item.price * item.quantity;
  }
  const tax = total * taxRate;
  return total + tax;
}

// Minified (320B) — Terser-ის შედეგი
function calculateTotalPrice(t,e){let l=0;for(let a=0;a<t.length;a++){const n=t[a];l+=n.price*n.quantity}return l+l*e}
```

### ინსტრუმენტები:
- **Terser** — ენა: JS, სიჩქარე: საშუალო, გამოყენება: webpack default
- **esbuild** — ენა: Go, სიჩქარე: ძალიან სწრაფი, გამოყენება: Vite default
- **SWC** — ენა: Rust, სიჩქარე: სწრაფი, გამოყენება: Next.js default
- **cssnano** — ენა: PostCSS, სიჩქარე: საშუალო, გამოყენება: CSS minification
- **Lightning CSS** — ენა: Rust, სიჩქარე: ძალიან სწრაფი, გამოყენება: Vite ახალი ვერსიები

### Build Tools-ში:
```javascript
// vite.config.js
export default {
  build: {
    minify: 'terser', // ან 'esbuild' (default, უფრო სწრაფი)
    terserOptions: {
      compress: {
        drop_console: true, // console.log-ების მოშორება production-ში
      },
    },
  },
};
```

## 2.2 კომპრესია (Compression)

### რა არის?
კომპრესია ამცირებს ფაილის ზომას ქსელში გადაცემამდე. სერვერი აკუმშავს, ბრაუზერი ხსნის.

### Gzip vs Brotli:

- **Gzip:**
  - შეკუმშვის ხარისხი: კარგი
  - სიჩქარე (compress): სწრაფი
  - სიჩქარე (decompress): სწრაფი
  - ბრაუზერის მხარდაჭერა: ყველა
  - HTTP Header: Content-Encoding: gzip
- **Brotli:**
  - შეკუმშვის ხარისხი: უკეთესი (20-30% მეტი)
  - სიჩქარე (compress): ნელი (static-ისთვის OK)
  - სიჩქარე (decompress): სწრაფი
  - ბრაუზერის მხარდაჭერა: თანამედროვე ყველა
  - HTTP Header: Content-Encoding: br

### როგორ ვნახოთ DevTools-ში:
Network tab → Response Headers:
```
Content-Encoding: br    ← Brotli გამოიყენება
Content-Length: 45230    ← შეკუმშული ზომა
```

### რეალური ზომის შედარება (ტიპიური React აპი):
```
Original:    450 KB
Minified:    180 KB  (60% reduction)
Gzipped:      55 KB  (88% reduction)
Brotli:       45 KB  (90% reduction)
```

### სერვერის კონფიგურაცია (Nginx):
```nginx
gzip on;                    # gzip compression ჩართე
gzip_types text/plain       # რა ტიპის ფაილებს აკომპრესირებს:
  text/css                  #   - CSS ფაილები
  application/json          #   - JSON მონაცემები
  application/javascript;   #   - JavaScript ფაილები
gzip_min_length 1000;       # 1000 ბაიტზე პატარა ფაილებს არ აკომპრესირებს
                            # (პატარა ფაილებზე compression overhead-ი მეტია ვიდრე სარგებელი)
```

## 2.3 Bundler-ის კონფიგურაცია

### რატომ გვჭირდება Build Tool საერთოდ?

ბრაუზერი მხოლოდ **HTML, CSS და ჩვეულებრივ JavaScript**-ს ესმის. მაგრამ თანამედროვე React-ში ჩვენ ვწერთ კოდს, რომელსაც ბრაუზერი პირდაპირ ვერ გაიგებს:

```jsx
// ბრაუზერს ეს არ ესმის!
import React from 'react'
import styles from './App.module.css'

function App() {
  return <div className={styles.container}>გამარჯობა</div>
}
```

- **JSX** — `<div>` JavaScript-ში სინტაქსური შეცდომაა ბრაუზერისთვის — ეს React-ის სინტაქსია, არა HTML
- **import/export** — მოდულური სისტემა — ძველ ბრაუზერებს საერთოდ არ ჰქონდათ, ახლებსაც შეზღუდვები აქვთ
- **CSS Modules, SASS** — ბრაუზერი მხოლოდ ჩვეულებრივ CSS-ს კითხულობს
- **TypeScript** — ბრაუზერს TypeScript საერთოდ არ ესმის

**Build tool** სწორედ ამ "თარგმანს" აკეთებს — შენს კოდს გარდაქმნის ბრაუზერთან თავსებად ფორმატში.

### რა ეტაპებს გადის კოდი?

```
შენი კოდი                           ბრაუზერისთვის მზა კოდი
─────────                           ──────────────────────
App.jsx    ─┐                       ┌─ bundle.js
Header.jsx ─┤                       ├─ styles.css
Footer.jsx ─┤  ► [ BUILD TOOL ] ►   ├─ chunk-1.js (lazy loaded)
App.css    ─┤                       └─ index.html
utils.ts   ─┘
```

1. **Transpilation** — JSX და TypeScript გარდაიქმნება ჩვეულებრივ JavaScript-ში (Babel, SWC, esbuild)
2. **Bundling** — ასობით ფაილი ერთიანდება რამდენიმე ფაილში
3. **Minification** — მცირდება ფაილის ზომა (იხ. სექცია 2.1)
4. **Code Splitting** — იქმნება ცალკე chunk-ები lazy-loaded კომპონენტებისთვის
5. **Tree Shaking** — გამოუყენებელი კოდი ამოიგდება საბოლოო bundle-დან

### Dev Server — რა არის და რატომ გვჭირდება?

Dev server არის ლოკალური სერვერი, რომელიც development-ის დროს ეშვება შენს კომპიუტერზე (`localhost:3000`). ის:

- **ემსახურება ფაილებს** — HTML/JS/CSS-ს მიაწვდის ბრაუზერს
- **HMR (Hot Module Replacement)** — კოდის შეცვლისას ბრაუზერი ავტომატურად განახლდება, გვერდის გადატვირთვის გარეშე
- **Transpilation რეალურ დროში** — JSX/TS ფაილებს პირდაპირ გარდაქმნის ბრაუზერთან თავსებად ფორმატში

### ევოლუცია — როგორ მივედით Vite-მდე

```
Grunt/Gulp (2012)  →  Webpack (2014)  →  Vite (2020)
  ხელით კონფიგი        ძლიერი, მაგრამ       სწრაფი, მარტივი
  ნელი                  რთული და ნელი        ნაგულისხმევად მუშაობს
```

**Webpack** — ყოველ ცვლილებაზე მთელ პროექტს თავიდან აწყობს. დიდ პროექტში 10-30 წამი.

**Vite** — development-ში საერთოდ არ აკეთებს bundling-ს. ბრაუზერს ES Modules-ით აძლევს ფაილებს ცალ-ცალკე. Bundling-ს მხოლოდ production build-ისთვის აკეთებს (Rollup-ით).

```
Webpack:  ფაილი შეიცვალა → მთელი bundle თავიდან → ბრაუზერი განახლდა (ნელი)
Vite:     ფაილი შეიცვალა → მხოლოდ ეს ფაილი განახლდა → მყისიერი (სწრაფი)
```

### რა არის Bundler?

Bundler არის build tool-ის ნაწილი, რომელიც აპლიკაციის ყველა ფაილს (JS, CSS, სურათები, ფონტები) აერთიანებს ოპტიმიზებულ output ფაილებში — bundle-ებში. ის ასევე ახორციელებს minification-ს, code splitting-ს, tree shaking-ს და სხვა ოპტიმიზაციებს.

### ძირითადი Bundler-ები:

- **Webpack** — ენა: JS, სიჩქარე: ნელი, მაგრამ მოქნილი, გამოყენება: CRA, Next.js (ადრე), enterprise
- **Vite** — ენა: Go (esbuild) + Rust (Rollup), სიჩქარე: ძალიან სწრაფი, გამოყენება: თანამედროვე React/Vue/Svelte
- **Parcel** — ენა: Rust, სიჩქარე: სწრაფი, გამოყენება: zero-config პროექტები
- **Turbopack** — ენა: Rust, სიჩქარე: ძალიან სწრაფი, გამოყენება: Next.js 15+

### Vite — კონფიგურაცია

Vite ყველაზე პოპულარული არჩევანია ახალი პროექტებისთვის. კონფიგურაცია მარტივია:

```javascript
// vite.config.js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({       // Vite-ის კონფიგურაციის ობიექტს ვაექსპორტებთ
                                    // defineConfig() მხოლოდ autocomplete-ს გვაძლევს IDE-ში
  plugins: [react()],               // React plugin — Vite-ს ასწავლის JSX-ის გაგებას
                                    // ამის გარეშე Vite ვერ გადათარგმნის <Button /> → React.createElement()
                                    // ასევე ჩართავს Fast Refresh-ს (ცვლილება → ბრაუზერი მაშინვე აახლებს)

  build: {
    // Minification
    minify: 'esbuild',            // default — ძალიან სწრაფი
    // minify: 'terser',          // უფრო აგრესიული შეკუმშვა, მაგრამ ნელი

    // Output directory
    outDir: 'dist',

    // Source Maps — production-ში debug-ისთვის
    // build-ის დროს იქმნება .map ფაილი (მაგ: bundle.js.map)
    // რომელიც minified კოდის თითოეულ ხაზს ორიგინალ ფაილთან აკავშირებს.
    // DevTools → Sources tab-ში ნახავ შენს ორიგინალ ფაილებს (App.jsx, Header.jsx)
    // და არა minified bundle.js-ს. error-ებიც ორიგინალ ხაზის ნომრებს აჩვენებს.
    //
    // true     — .map იქმნება და ბრაუზერი ავტომატურად ტვირთავს (ყველას შეუძლია ნახოს შენი კოდი)
    // 'hidden' — .map იქმნება მაგრამ bundle-ში ლინკი არ ჩაიწერება (მხოლოდ შენ ხელით ატვირთავ)
    // false    — .map საერთოდ არ იქმნება
    sourcemap: true,

    // Chunk ზომის ლიმიტი (KB) — გაფრთხილება თუ გადააჭარბებს
    chunkSizeWarningLimit: 500,

    // Rollup-ის კონფიგურაცია (Vite Rollup-ს იყენებს production build-ისთვის)
    rollupOptions: {
      output: {
        // ხელით chunk-ებად დაყოფა — vendor ბიბლიოთეკების გამოყოფა
        manualChunks: {
          'react-vendor': ['react', 'react-dom'],
          'router': ['react-router-dom'],
          'charts': ['chart.js', 'recharts'],
        },
      },
    },
  },

  // Dev Server
  server: {
    port: 3000,
    open: true,                   // ბრაუზერის ავტომატურად გახსნა
  },
});
```

#### manualChunks — რატომ არის მნიშვნელოვანი?

```
❌ manualChunks-ის გარეშე:
  index-Da3x1.js (650KB)     ← ყველაფერი ერთად: React + Router + Charts + აპის კოდი

✅ manualChunks-ით:
  react-vendor-Bk2x.js (140KB)  ← React — იშვიათად იცვლება, კარგად cache-დება
  router-Cx4z.js (30KB)          ← Router — ცალკე cache
  charts-Ey7w.js (200KB)         ← Charts — მხოლოდ Analytics გვერდზე ჩაიტვირთება
  index-Fa9q.js (80KB)           ← აპის კოდი — ხშირად იცვლება, პატარაა
```

**უპირატესობა**: როცა აპის კოდს ცვლი, მომხმარებელს მხოლოდ `index-*.js` უახლდება. `react-vendor` და `charts` ბრაუზერის cache-დან წამოიღებს — არ ჩამოტვირთავს ხელახლა.

### Webpack — კონფიგურაცია

Webpack უფრო verbose-ია, მაგრამ მეტ კონტროლს იძლევა:

```javascript
// webpack.config.js
// Webpack-ის კონფიგურაცია — ეუბნება build tool-ს როგორ დაამუშაოს შენი კოდი.
// ეს ფაილი იკითხება npm run build და npm run dev ბრძანებებზე.

const path = require('path');                                    // Node.js-ის მოდული ფაილის path-ებისთვის
const HtmlWebpackPlugin = require('html-webpack-plugin');        // HTML ფაილის ავტომატური გენერაცია
const MiniCssExtractPlugin = require('mini-css-extract-plugin'); // CSS-ის ცალკე ფაილად ამოღება (inline-ის ნაცვლად)
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer'); // bundle-ის ზომის ვიზუალური ანალიზი

module.exports = {
  // ═══ MODE ═══
  // production — ჩართავს minification-ს, tree shaking-ს, ოპტიმიზაციებს
  // development — source map-ები, სწრაფი build, readable კოდი (არ ამინიფიცირებს)
  // Webpack-ი mode-ის მიხედვით ავტომატურად ჩართავს/გამორთავს ოპტიმიზაციებს.
  // ანუ ეს ერთი ხაზი ბევრ რამეს აკონტროლებს — dev-ზე debug-ისთვის მორგებულია,
  // production-ზე კი სიჩქარისა და ზომის ოპტიმიზაციისთვის.
  mode: 'production',

  // ═══ ENTRY ═══
  // საიდან დაიწყოს Webpack-მა ფაილების კითხვა.
  // ამ ფაილიდან import-ების მიყოლებით იპოვის ყველა საჭირო ფაილს.
  entry: './src/index.js',

  // ═══ OUTPUT ═══
  // სად და როგორ ჩაწეროს საბოლოო bundle.
  output: {
    path: path.resolve(__dirname, 'dist'),         // dist/ ფოლდერში ჩაწერს
    filename: '[name].[contenthash].js',            // contenthash — ფაილის შიგთავსიდან გენერირებული hash.
                                                    // შიგთავსი შეიცვალა → hash იცვლება → ბრაუზერი ახლიდან ჩამოტვირთავს.
                                                    // არ შეცვლილა → იგივე hash → cache-დან წაიკითხავს. (cache busting)
    clean: true,                                    // build-ის წინ dist/ ფოლდერს გაასუფთავებს ძველი ფაილებისგან
  },

  // ═══ LOADERS ═══
  // Webpack-ს თავისთავად მხოლოდ JS ესმის.
  // Loader-ები ასწავლიან სხვა ტიპის ფაილების დამუშავებას.
  module: {
    rules: [
      {
        test: /\.jsx?$/,                 // ყველა .js და .jsx ფაილი
        exclude: /node_modules/,         // node_modules-ს არ ეხება (უკვე დამუშავებულია)
        use: 'babel-loader',             // Babel-ით გარდაქმნის: JSX → JS, ახალი JS → ძველი JS
      },
      {
        test: /\.css$/,                  // ყველა .css ფაილი
        use: [
          MiniCssExtractPlugin.loader,   // CSS-ს ცალკე ფაილად ამოიღებს (არა inline <style>-ში)
          'css-loader',                  // CSS-ში import-ებს და url()-ებს resolve-ს უკეთებს
        ],
      },
      {
        test: /\.(png|jpg|gif|svg)$/,    // სურათები
        type: 'asset',                   // Webpack-ის built-in asset handling
        parser: {
          dataUrlCondition: {
            maxSize: 8 * 1024,           // 8KB-ზე პატარა სურათი → base64 inline (ცალკე request არ სჭირდება)
          },                             // 8KB-ზე დიდი → ცალკე ფაილად dist/-ში
        },
      },
    ],
  },

  // ═══ PLUGINS ═══
  // Loader-ები ცალკეულ ფაილებს ამუშავებს, Plugin-ები კი მთლიან build პროცესს აკონტროლებს.
  plugins: [
    new HtmlWebpackPlugin({
      template: './public/index.html',   // შენი HTML template-ის მიხედვით გენერირებს index.html-ს
    }),                                  // ავტომატურად ჩასვამს <script> და <link> ტეგებს bundle-ისთვის
    new MiniCssExtractPlugin({
      filename: '[name].[contenthash].css',  // CSS ფაილსაც contenthash-ს მისცემს cache busting-ისთვის
    }),
    // new BundleAnalyzerPlugin(),       // გააკომენტარე და გაუშვი — ბრაუზერში გაიხსნება ვიზუალური რუკა
  ],                                     // რომელიც აჩვენებს რომელი ბიბლიოთეკა რამდენს იკავებს bundle-ში

  // ═══ OPTIMIZATION ═══
  // ავტომატური code splitting-ის კონფიგურაცია.
  optimization: {
    splitChunks: {
      chunks: 'all',                     // ყველა ტიპის import-ზე (sync და async) გაყოფს
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/, // node_modules-დან მომავალ ბიბლიოთეკებს
          name: 'vendors',               // ცალკე vendors.js ფაილში გამოყოფს
          chunks: 'all',                 // ეს Vite-ის manualChunks-ის ანალოგია
        },
      },
    },
  },

  // Source Maps
  devtool: 'source-map',         // production: 'source-map' | 'hidden-source-map'
};
```

### Webpack vs Vite — პრაქტიკული შედარება

- **Config სირთულე** — Webpack: მაღალი — loaders, plugins ხელით; Vite: დაბალი — ბევრი default-ად
- **Dev server სიჩქარე** — Webpack: ნელი (მთლიანი bundle rebuild); Vite: მყისიერი (ESM + HMR)
- **Production build** — Webpack: ნელი, მაგრამ stable; Vite: Rollup (სწრაფი, ოპტიმალური)
- **Code Splitting** — Webpack: `splitChunks` კონფიგურაცია; Vite: `manualChunks` ან ავტომატური
- **Tree Shaking** — Webpack: მუშაობს, მაგრამ ხანდახან დახმარება სჭირდება; Vite: default-ად ეფექტური
- **Ecosystem** — Webpack: უზარმაზარი plugin ecosystem; Vite: მზარდი, მაგრამ ნაკლები

### Environment Variables

```javascript
// .env
VITE_API_URL=https://api.example.com    // Vite — VITE_ პრეფიქსი სავალდებულოა
REACT_APP_API_URL=https://api.example.com  // CRA (Webpack) — REACT_APP_ პრეფიქსი

// გამოყენება კოდში:
// Vite
const apiUrl = import.meta.env.VITE_API_URL;

// Webpack (CRA)
const apiUrl = process.env.REACT_APP_API_URL;
```

### Build ანალიზი — პრაქტიკული ბრძანებები

```bash

npm run build
# dist/ ფოლდერში ნახავ ფაილებს ზომებით

npx source-map-explorer dist/assets/*.js
```
