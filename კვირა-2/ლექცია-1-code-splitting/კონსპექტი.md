# ლექცია 1 — კოდის დაყოფა (Code Splitting)

## 1.1 რა არის Code Splitting?

Code Splitting გულისხმობს JavaScript bundle-ის დაყოფას მცირე ნაწილებად (chunks), რათა მომხმარებელმა ჩატვირთოს მხოლოდ ის კოდი, რომელიც მას ამ მომენტში სჭირდება.

### რატომ არის მნიშვნელოვანი?

წარმოიდგინე ონლაინ მაღაზია: მომხმარებელი მთავარ გვერდზე შემოდის, მაგრამ ბრაუზერი მას Admin Panel-ის, Checkout-ის, User Settings-ის კოდსაც ატვირთინებს — 500KB-1MB+ JavaScript-ს. მომხმარებელს ეს კოდი არ სჭირდება, მაგრამ მაინც ელოდება ჩატვირთვას. ნელი ინტერნეტით (მობილური, 3G) ეს განსაკუთრებით მტკივნეულია — 3+ წამი ლოდინი და მომხმარებელი უბრალოდ ტოვებს საიტს.

Code Splitting-ით თითოეული გვერდის/კომპონენტის კოდი ცალკე ფაილში (chunk) ექცევა და მხოლოდ მაშინ იტვირთება, როცა ნამდვილად საჭიროა.

## 1.2 JavaScript-ის import-ების ტიპები

სანამ Code Splitting-ზე გადავალთ, მნიშვნელოვანია გავიგოთ import-ების სამი ძირითადი ტიპი, რადგან Code Splitting სწორედ import-ების ტიპის შეცვლაზეა დაფუძნებული.

### Named Export vs Default Export — ბრეისებიანი და ბრეისების გარეშე import

სანამ import-ების ტიპებზე გადავალთ, გავარკვიოთ რატომ იწერება ზოგი import ქარლი ბრეისებით `{ }` და ზოგი — მათ გარეშე. ეს დამოკიდებულია იმაზე, თუ როგორ არის ექსპორტირებული:

```javascript
// math.js — ერთ ფაილში რამდენიმე რამ ექსპორტდება
export function add(a, b) { return a + b; }        // named export
export function subtract(a, b) { return a - b; }   // named export

// import-ისას ბრეისებით ირჩევ რა გინდა
import { add } from './math';              // მხოლოდ add
import { add, subtract } from './math';    // ორივე
```

```javascript
// Dashboard.jsx — ფაილს ერთი მთავარი რამ ექსპორტავს
export default function Dashboard() { ... }   // default export

// import-ისას ბრეისები არ სჭირდება, და სახელს შენ ირჩევ
import Dashboard from './Dashboard';
import MyPage from './Dashboard';       // იგივეა, სახელი შენზეა
```

ორივე ერთადაც შეიძლება:
```javascript
import React, { Suspense, lazy } from 'react';
//     ↑                              ↑
//     default export                 named exports
//     (ბრეისის გარეშე)               (ბრეისებში)
```

- `export default X` → `import X from '...'` — ბრეისების **გარეშე**
- `export function X` → `import { X } from '...'` — ბრეისებით **შიგნით**
- ორივე ერთად → `import Default, { Named } from '...'` — default გარეთ, named შიგნით

### Static Import (სტატიკური)

ფაილის თავში იწერება. Bundler-ი (Webpack, Vite) build-ისას ყველა static import-ს **ერთ ფაილში აერთიანებს**.

```javascript
import { add } from './math';
import Dashboard from './pages/Dashboard';
```

- ყოველთვის ჩაიტვირთება, მიუხედავად იმისა გამოიყენება თუ არა ამ სესიაში
- Bundler-ს შეუძლია Tree Shaking-ის გაკეთება (იხ. სექცია 1.8)
- გამოიყენე ყველაფრისთვის, რაც აუცილებლად საჭიროა გვერდის ჩატვირთვისას

### Dynamic Import (დინამიკური)

კოდის ნებისმიერ ადგილას შეიძლება გამოძახება. აბრუნებს **Promise**-ს — ანუ ასინქრონულად მუშაობს და ცალკე chunk-ს ქმნის.

```javascript
// ჩაიტვირთება მხოლოდ მაშინ, როცა მომხმარებელი ღილაკს დააჭერს
document.getElementById('exportBtn').addEventListener('click', async () => {
  const { exportToCSV } = await import('./csvExporter');
  exportToCSV(data);
});
```

- ცალკე ფაილს (chunk) ქმნის build-ისას
- იტვირთება მხოლოდ მაშინ, როცა კოდი შესრულდება
- **ნებისმიერი** ფაილისთვის მუშაობს: კომპონენტი, utility ფუნქცია, ბიბლიოთეკა, JSON

### React.lazy — Dynamic Import-ის wrapper კომპონენტებისთვის

React.lazy არის React-ის მოხერხებული wrapper, რომელიც dynamic import-ს იღებს და React კომპონენტად აქცევს. შიგნით სწორედ `import()` გამოიყენება.

```jsx
// ❌ უბრალო dynamic import — აბრუნებს Promise-ს, მაგრამ React-ს არაფერი ესმის ამისგან.
//    ვერ დაწერ <dashboardPromise /> — ეს კომპონენტი არ არის
const dashboardPromise = import('./pages/Dashboard');

// ✅ React.lazy — შიგნით იგივე import()-ს იყენებს, მაგრამ React-ის კომპონენტად აქცევს.
//    იცის როგორ დაელოდოს chunk-ს, როგორ აჩვენოს Suspense fallback,
//    და როგორ დარენდეროს კომპონენტი chunk-ის ჩატვირთვის შემდეგ
const Dashboard = lazy(() => import('./pages/Dashboard'));
```

**მთავარი განსხვავება:** `React.lazy` მხოლოდ React კომპონენტებისთვის მუშაობს (default export). utility ფუნქციის, JSON-ის ან სხვა მნიშვნელობის lazy-ით ჩატვირთვა არ შეიძლება — ამისთვის პირდაპირ `import()` გამოიყენე.

### შეჯამება — რომელი import რისთვის?

- **Static** — `import X from './X'`
  - როდის იტვირთება: ყოველთვის, build-ისას ერთ bundle-ში
  - რისთვის: ყველაფერი რაც საწყის გვერდზე საჭიროა

- **Dynamic** — `await import('./X')`
  - როდის იტვირთება: მხოლოდ როცა ეს ხაზი შესრულდება
  - რისთვის: ნებისმიერი — ფუნქცია, კლასი, JSON, კომპონენტი

- **React.lazy** — `lazy(() => import('./X'))`
  - როდის იტვირთება: როცა კომპონენტი პირველად გამოჩნდება
  - რისთვის: **მხოლოდ** React კომპონენტები

## 1.3 React.lazy() და Suspense

### როგორ მუშაობს?

1. `React.lazy()` იღებს ფუნქციას, რომელიც `import()`-ს აბრუნებს
2. პირველად როცა კომპონენტი უნდა გამოჩნდეს, React იწყებს chunk-ის ჩატვირთვას
3. სანამ chunk ჩაიტვირთება, `<Suspense>`-ის `fallback` ჩანს (loading spinner, skeleton და ა.შ.)
4. chunk რომ ჩაიტვირთება, ნამდვილი კომპონენტი ჩანს

```jsx
import React, { Suspense, lazy } from 'react';

// ❌ ჩვეულებრივი import — Dashboard-ისა და Settings-ის კოდი საწყის bundle-შია,
//    მიუხედავად იმისა, მომხმარებელი ამ გვერდებს მოინახულებს თუ არა
// import Dashboard from './pages/Dashboard';
// import Settings from './pages/Settings';

// ✅ Lazy import — თითოეული გვერდი ცალკე chunk-ში გადადის.
//    Dashboard-ის კოდი ჩაიტვირთება მხოლოდ /dashboard-ზე გადასვლისას
const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings = lazy(() => import('./pages/Settings'));

function App() {
  return (
    // Suspense აუცილებელია — lazy კომპონენტი ასინქრონულად იტვირთება,
    // fallback ჩანს სანამ chunk მოვა ქსელიდან.
    // Suspense-ის გარეშე React error-ს დაისვრის და აპლიკაცია გაითიშება:
    // "A component suspended while rendering, but no Suspense boundary was found"
    // React-მა იცის რომ chunk ჯერ არ მოსულა, მაგრამ არ იცის რა აჩვენოს
    // ლოდინის დროს — Suspense სწორედ ამას ეუბნება.
    <Suspense fallback={<div>იტვირთება...</div>}>
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
```

## 1.4 Route-based vs Component-based Splitting

### Route-based — გვერდების დონეზე დაყოფა (ყველაზე გავრცელებული)

ყოველი route/გვერდი ცალკე chunk-ად გამოიყოფა. ეს ყველაზე ბუნებრივია, რადგან მომხმარებელი ერთ გვერდს ხედავს და სხვა გვერდების კოდი არ სჭირდება.

```jsx
const Home = lazy(() => import('./pages/Home'));
const About = lazy(() => import('./pages/About'));
const Products = lazy(() => import('./pages/Products'));
const Cart = lazy(() => import('./pages/Cart'));
```

### Component-based — მძიმე კომპონენტების დონეზე დაყოფა

ზოგჯერ ერთ გვერდზეც კი არის კომპონენტი, რომელიც მძიმეა და არ ჩანს პირველივე ჩატვირთვისას (მაგ. chart, rich text editor, map). ასეთი კომპონენტიც ცალკე chunk-ად გამოიყოფა.

```jsx
const HeavyChart = lazy(() => import('./components/HeavyChart'));

function ArticlePage() {
  const [showChart, setShowChart] = useState(false);
  
  return (
    <div>
      <article>...</article>
      <button onClick={() => setShowChart(true)}>გრაფიკის ჩვენება</button>

      {/* HeavyChart-ის კოდი ჩაიტვირთება მხოლოდ ღილაკზე click-ისას,
          არა გვერდის გახსნისას */}
      {showChart && (
        <Suspense fallback={<div>გრაფიკი იტვირთება...</div>}>
          <HeavyChart />
        </Suspense>
      )}
    </div>
  );
}
```

### Dynamic Import არა-კომპონენტებისთვის (utility ფუნქციები, ბიბლიოთეკები)

React.lazy მხოლოდ კომპონენტებისთვისაა, მაგრამ dynamic `import()` **ნებისმიერი** JavaScript მოდულისთვის მუშაობს. თუ გვაქვს მძიმე utility ფაილი, რომელიც მხოლოდ კონკრეტულ მოქმედებაზე სჭირდება:

```jsx
// ❌ ჩვეულებრივი import — generateReport (50KB+) ყოველთვის bundle-შია,
//    მიუხედავად იმისა მომხმარებელი ანგარიშს დააგენერირებს თუ არა
import { generateReport } from '../utils/heavyUtils';

// ✅ Dynamic import — heavyUtils ცალკე chunk-ად გამოიყოფა და
//    მხოლოდ ღილაკზე click-ისას ჩაიტვირთება
const handleGenerateReport = async () => {
  const { generateReport } = await import('../utils/heavyUtils');
  setReport(generateReport());
};
```

## 1.5 Trade-off: საწყისი bundle vs შემდგომი ჩატვირთვა

ბუნებრივი კითხვაა: "საწყის bundle-ს ვამცირებ, მაგრამ სხვა გვერდზე გადასვლისას ხომ ახალი chunk იტვირთება — ეს ხომ ნელია?" 

დიახ, ტექნიკურად სხვა გვერდზე გადასვლისას ახალი network request ხდება. მაგრამ ეს trade-off მაინც მომგებიანია:

- **საწყისი ჩატვირთვა (First Load) ყველაზე კრიტიკულია.** მომხმარებელი თუ ვერ ნახავს პირველ გვერდს სწრაფად, სხვა გვერდებამდე საერთოდ ვერ მივა. Google-ის კვლევით, 53% მობილური მომხმარებელი ტოვებს საიტს, თუ 3 წამზე მეტი ეტვირთება.
- **chunk-ები პატარაა.** Settings-ის chunk შეიძლება 3-5KB იყოს, არა მთლიანი 500KB bundle. პატარა ფაილი წამის მეასედებში იტვირთება.
- **ბრაუზერი cache-ავს chunk-ებს.** მეორეჯერ Settings-ზე გადასვლისას network request საერთოდ არ ხდება — ბრაუზერის cache-იდან მყისიერად იტვირთება.
- **Prefetch-ით საერთოდ შეუმჩნეველი ხდება** — ამას ქვემოთ ვნახავთ.

## 1.6 Prefetch და Preload — chunk-ების წინასწარი ჩატვირთვა

Prefetch საშუალებას გვაძლევს chunk-ები **ფონურად წინასწარ** ჩავტვირთოთ, სანამ მომხმარებელი ჯერ კიდევ მიმდინარე გვერდს კითხულობს. ასე რომ, როცა შემდეგ გვერდზე გადავა, chunk უკვე მზადაა და ლოდინი საერთოდ არ იქნება.

### Prefetch vs Preload — რა განსხვავებაა?

**Prefetch:**
- პრიორიტეტი: დაბალი — ბრაუზერი ტვირთავს, როცა თავისუფალია (idle time)
- როდის: მიმდინარე გვერდის ჩატვირთვის **შემდეგ**
- რისთვის: შემდეგი გვერდის/მოქმედების რესურსები
- ინტერაქტივობა: **არ აფერხებს** — ბრაუზერი მხოლოდ თავისუფალ დროს ტვირთავს

**Preload:**
- პრიორიტეტი: მაღალი — დაუყოვნებლივ იტვირთება
- როდის: მიმდინარე გვერდის ჩატვირთვასთან **ერთად**
- რისთვის: მიმდინარე გვერდისთვის საჭირო კრიტიკული რესურსები
- ინტერაქტივობა: შეიძლება შეანელოს, თუ ბევრ რამეს ტვირთავ

### აფერხებს თუ არა ინტერაქტივობას?

**Prefetch — არა.** ბრაუზერი prefetch-ს ყველაზე დაბალი პრიორიტეტით აკეთებს. თუ მომხმარებელი ღილაკს აჭერს, ფორმას ავსებს ან scroll-ავს — ეს მოქმედებები უპირატესობას იღებენ. Prefetch ხდება მხოლოდ მაშინ, როცა ბრაუზერს სხვა არაფერი აქვს საკეთებელი (idle time). ამიტომ მიმდინარე გვერდის interactivity-ს საერთოდ არ ეხება.

**Preload — ფრთხილად.** Preload მაღალი პრიორიტეტით ტვირთავს და bandwidth-ს იკავებს. თუ ბევრ რამეს preload-ავ, შეიძლება მიმდინარე გვერდის სხვა რესურსები შეანელოს.

### Webpack-ში: Magic Comments

Webpack-ი ცნობს სპეციალურ კომენტარებს `import()` შიგნით — ამას **magic comments** ეწოდება. ეს ჩვეულებრივი კომენტარი არ არის — Webpack-ი build-ისას კითხულობს მას და მის მიხედვით მოქმედებს.

```jsx
// webpackPrefetch: true — Webpack-ს ეუბნები: "ეს chunk ალბათ მალე დამჭირდება,
// ფონურად ჩატვირთე, როცა მთავარი გვერდი მზად იქნება"
const Settings = lazy(() => import(/* webpackPrefetch: true */ './pages/Settings'));

// webpackPreload: true — "ეს chunk ახლავე მჭირდება, მთავარ bundle-თან ერთად ჩატვირთე"
const CriticalChart = lazy(() => import(/* webpackPreload: true */ './components/CriticalChart'));
```

რა ხდება build-ისას? Webpack ავტომატურად ამატებს HTML-ში `<link>` ტეგს:
```html
<!-- prefetch-ისთვის — დაბალი პრიორიტეტი, idle დროს -->
<link rel="prefetch" href="/static/js/Settings.chunk.js">

<!-- preload-ისთვის — მაღალი პრიორიტეტი, დაუყოვნებლივ -->
<link rel="preload" href="/static/js/CriticalChart.chunk.js" as="script">
```

### Vite-ში: ავტომატური Preload + ხელით Prefetch

Vite სხვანაირად მუშაობს — **magic comments არ აქვს**, რადგან Vite Rollup-ს იყენებს build-ისთვის, არა Webpack-ს.

**ავტომატური:** Vite build-ისას ავტომატურად ამატებს `<link rel="modulepreload">` ტეგებს იმ chunk-ებისთვის, რომლებიც მიმდინარე გვერდისთვის საჭიროა.

**Prefetch ხელით:** სხვა გვერდების chunk-ების prefetch-ისთვის რამდენიმე მიდგომაა:

```jsx
// 1. ხელით prefetch — მაგ. hover-ისას ან idle დროს
const prefetchSettings = () => {
  import('./pages/Settings'); // ეს საკმარისია — chunk ჩაიტვირთება და cache-ში დარჩება
};

// მაგ. ლინკზე hover-ისას წინასწარ ჩატვირთვა
<Link to="/settings" onMouseEnter={prefetchSettings}>Settings</Link>

// 2. requestIdleCallback — ბრაუზერს ვეუბნებით "როცა თავისუფალი იქნები, ეს ჩატვირთე"
requestIdleCallback(() => {
  import('./pages/Settings');
  import('./pages/Dashboard');
});
```

## 1.7 როდის გამოვიყენოთ Code Splitting?

### რისთვის გამოიყენება lazy / dynamic import?

**ღირს:**
- **გვერდები (routes)** — Dashboard, Settings, AdminPanel — თითქმის ყოველთვის
- **მძიმე კომპონენტები** — Chart library, rich text editor, map
- **პირობითი UI** — Modal/dialog რომელიც მძიმე ბიბლიოთეკას იყენებს
- **მძიმე utility ფუნქციები** — PDF generator, CSV exporter, crypto — `import()`-ით

**არ ღირს:**
- **მცირე კომპონენტები** — Button, Card, Header
- **ყველგან გამოყენებული კოდი** — Auth context, API client, layout

**წესი:** თუ კოდი >30-50KB-ია და არ სჭირდება პირველივე ჩატვირთვისას — splitting-ის კანდიდატია. თუ პატარაა ან ყოველთვის საჭიროა — ჩვეულებრივი import ჯობია, რადგან splitting-ს საკუთარი overhead აქვს (Suspense, fallback, ახალი network request, chunk ფაილის ზომა).

## 1.8 Tree Shaking

Tree Shaking არის bundler-ის უნარი, ამოიღოს bundle-იდან ის კოდი, რომელიც არსად გამოიყენება. წარმოიდგინე ხეს რომ ანჯღრევ — მხოლოდ მშრალი (გამოუყენებელი) ფოთლები ცვივა, ცოცხალი რჩება.

### როგორ მუშაობს?

```javascript
// math.js — სამი ფუნქცია ექსპორტდება
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }
export function multiply(a, b) { return a * b; }

// app.js — მხოლოდ add გამოიყენება
import { add } from './math';
console.log(add(2, 3));
```

Build-ისას bundler-ი (Webpack, Vite/Rollup) ხედავს, რომ `subtract` და `multiply` არსად გამოიყენება და **საბოლოო bundle-იდან ამოიღებს მათ**. შედეგი — უფრო პატარა ფაილი.

### რა პირობებში მუშაობს Tree Shaking?

Tree Shaking მუშაობს მხოლოდ მაშინ, როცა **ორივე მხარე** ES Modules-ს იყენებს — **შენი კოდიც** და **ბიბლიოთეკაც შიგნიდან**:

```javascript
// ✅ ES Modules — Tree Shaking მუშაობს
import { add } from './math';

// ❌ CommonJS — Tree Shaking ვერ მუშაობს, მთელი ფაილი bundle-შია
const { add } = require('./math');
```

**მნიშვნელოვანი**: `import` სინტაქსი შენს კოდში საკმარისი არ არის! ბიბლიოთეკაც უნდა იყოს ES Modules ფორმატში **შიგნიდან**. თუ ბიბლიოთეკა CommonJS-ითაა დაწერილი, bundler-ი ვერ გააანალიზებს მას — თუნდაც შენ `import` დაწერო.

**რატომ?** CommonJS-ში `require` შეიძლება პირობითად გამოიძახო (`if (x) require('y')`) და bundler-ი ვერ გაარკვევს build-ისას რა იქნება საჭირო — ამიტომ მთლიან ფაილს ტოვებს. ES Modules-ში `import` ყოველთვის ფაილის თავშია, პირობის გარეშე — bundler-ი ზუსტად ხედავს რა არის საჭირო.

### პრაქტიკული მაგალითი: ბიბლიოთეკების სწორი import

ბიბლიოთეკის import-ის ფორმატს უზარმაზარი გავლენა აქვს bundle-ის ზომაზე:

```javascript
// ❌ მთლიანი lodash — ~70KB+ bundle-ში, მაშინაც კი თუ 1 ფუნქცია გჭირდება
import { orderBy } from 'lodash';

// ✅ lodash-es (ES Modules ვერსია) — Tree Shaking მუშაობს, მხოლოდ orderBy რჩება
import { orderBy } from 'lodash-es';

// ✅ ალტერნატივა — კონკრეტული ფაილის პირდაპირი import
import orderBy from 'lodash-es/orderBy';
```

**რატომ არ მუშაობს `import { orderBy } from 'lodash'`?**

შენ `import` სინტაქსს იყენებ — მაგრამ `lodash` პაკეტი **შიგნიდან** CommonJS-ითაა დაწერილი:

```javascript
// lodash შიგნით — CommonJS:
module.exports = { orderBy: ..., groupBy: ..., map: ..., /* 300+ ფუნქცია */ }
// bundler ხედავს ერთ დიდ ობიექტს — ვერ არკვევს რა ამოაგდოს

// lodash-es შიგნით — ES Modules:
export function orderBy() { ... }
export function groupBy() { ... }
export function map() { ... }
// bundler ხედავს ცალ-ცალკე export-ებს — ზუსტად იცის რომელი წაშალოს
```

**შენ არ აკეთებ Tree Shaking-ს** — bundler ავტომატურად აკეთებს build-ისას. შენი საქმე მხოლოდ ისაა, რომ ისეთი ბიბლიოთეკა აირჩიო, რომელიც ES Modules ფორმატშია.

### Tree Shaking-ის ჩეკლისტი

- გამოიყენე `import`/`export`, არა `require`/`module.exports`
- ბიბლიოთეკების `-es` ვერსიები ამჯობინე (`lodash-es`, `date-fns` და ა.შ.)
- package.json-ში `"sideEffects": false` ეხმარება bundler-ს უფრო აგრესიული Tree Shaking-ის გაკეთებაში

### რას ნიშნავს `sideEffects: false`?

**Side effect** — კოდი, რომელიც რაღაცას აკეთებს მხოლოდ import-ით, ექსპორტის გამოყენების გარეშე:

```javascript
import './polyfill.js';    // არაფერს ვიყენებ, მაგრამ ფაილი Array.prototype-ს ცვლის
import './analytics.js';   // import-ზე თვითონ აგზავნის tracking event-ს
import './styles.css';     // CSS-ს ამატებს გვერდზე
```

Bundler-ი **ფრთხილია** — თუ ფაილი import-ითაა, მაგრამ ვერცერთი export არ გამოიყენება, bundler მაინც **ტოვებს** ფაილს, რადგან ფიქრობს: "იქნებ side effect აქვს — წავშალო და რაღაც გაფუჭდეს?"

```json
// package.json
{
  "sideEffects": false
}
```

ეს ბიბლიოთეკის ავტორის **გარანტიაა** bundler-ისთვის: "ჩემი არცერთი ფაილი side effect-ს არ აკეთებს — თუ export არ გამოიყენება, თამამად წაშალე."

**"უფრო აგრესიული Tree Shaking"** = bundler-ი მეტ ფაილს ამოაგდებს bundle-იდან, რადგან აღარ ფრთხილობს side effect-ების გამო.
