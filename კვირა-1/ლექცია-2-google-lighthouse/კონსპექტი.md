# ლექცია 2 — Google Lighthouse

## 2.1 რა არის Lighthouse?

Lighthouse არის Google-ის ღია კოდის ავტომატიზირებული ინსტრუმენტი, რომელიც აანალიზებს ვებგვერდის ხარისხს რამდენიმე კატეგორიით (Performance, Accessibility, Best Practices, SEO).

## 2.2 როგორ გამოვიყენოთ?

1. გახსენით DevTools (F12 ან Cmd+Option+I)
2. გადადით Lighthouse tab-ზე
3. აირჩიეთ Mode, კატეგორიები და მოწყობილობა (Mobile/Desktop)
4. დააჭირეთ "Analyze page load"

## 2.3 რეჟიმები (Modes)

Lighthouse-ს სამი რეჟიმი აქვს, რომლებიც გვერდის სხვადასხვა ასპექტს ამოწმებს:

### Navigation (Default)
**რა აკეთებს:** სრულად ტვირთავს გვერდს თავიდან ბოლომდე და ზომავს ჩატვირთვის მთელ პროცესს — დასაწყისიდან ბოლომდე.

ეს არის კლასიკური რეჟიმი. Lighthouse ხელახლა ტვირთავს გვერდს და ზომავს ყველაფერს: FCP, LCP, CLS, TBT და ა.შ. ესაა ის რეჟიმი, რომელიც Performance ქულას გვაძლევს.

### Timespan
**რა აკეთებს:** ზომავს გვერდზე მომხმარებლის ინტერაქციის პერიოდს — არა ჩატვირთვას, არამედ მის შემდეგ რა ხდება.

მაგალითად: მომხმარებელმა დააჭირა ღილაკს, გადაასქროლა, გახსნა მოდალი — ეს რეჟიმი ამ მონაკვეთს აანალიზებს. გამოსადეგია SPA (Single Page Application) ტიპის საიტებზე, სადაც გვერდი ერთხელ იტვირთება და შემდეგ მომხმარებელი შიგნით მოქმედებს.

### Snapshot
**რა აკეთებს:** იღებს გვერდის მიმდინარე მდგომარეობის "სურათს" და აანალიზებს — არც ტვირთავს გვერდს თავიდან, არც ინტერაქციას ელოდება.

გამოსადეგია როცა გვინდა მხოლოდ ამჟამინდელი მდგომარეობის შემოწმება: accessibility პრობლემები, SEO ტეგები, Best Practices. Performance-ის ქულას ეს რეჟიმი არ ზომავს.

### რა აქვთ საერთო?
სამივე რეჟიმი ერთსა და იმავე Lighthouse ინსტრუმენტს იყენებს და ერთსა და იმავე audit-ებს ამოწმებს (Accessibility, SEO, Best Practices). განსხვავება მხოლოდ იმაშია, **როდის და რა მონაკვეთს** აანალიზებენ.

### რა განსხვავებაა?
- **Navigation:**
  - გვერდის ხელახალი ჩატვირთვა: დიახ
  - Performance ქულა: დიახ
  - Accessibility/SEO: დიახ
  - როდის გამოიყენება: ჩატვირთვის ანალიზი
- **Timespan:**
  - გვერდის ხელახალი ჩატვირთვა: არა
  - Performance ქულა: ნაწილობრივ
  - Accessibility/SEO: დიახ
  - როდის გამოიყენება: ინტერაქციის ანალიზი
- **Snapshot:**
  - გვერდის ხელახალი ჩატვირთვა: არა
  - Performance ქულა: არა
  - Accessibility/SEO: დიახ
  - როდის გამოიყენება: მიმდინარე მდგომარეობა

## 2.4 კატეგორიები (Categories)

### Performance
ზომავს **რამდენად სწრაფად** იტვირთება და რეაგირებს გვერდი. მოიცავს:
- ჩატვირთვის მეტრიკებს (FCP, LCP, Speed Index)
- ინტერაქტივობას (TBT — main thread-ის დაბლოკვა)
- ვიზუალურ სტაბილურობას (CLS — layout shift-ები)

### Accessibility
ზომავს **რამდენად ხელმისაწვდომია** გვერდი შეზღუდული შესაძლებლობების მქონე ადამიანებისთვის. მოიცავს:
- alt ატრიბუტების არსებობა სურათებზე
- ფორმის ელემენტების label-ები
- კონტრასტის თანაფარდობა (ტექსტი vs ფონი)
- კლავიატურით ნავიგაცია
- ARIA ატრიბუტების სწორი გამოყენება

### Best Practices
ზომავს **იცავს თუ არა** გვერდი ვებ-დეველოპმენტის საუკეთესო პრაქტიკებს. მოიცავს:
- HTTPS-ის გამოყენება
- console-ში error-ების არარსებობა
- მოძველებული API-ების თავიდან აცილება
- სურათების სწორი რეზოლუცია
- source map-ების არსებობა

### SEO
ზომავს **რამდენად კარგად** არის გვერდი ოპტიმიზირებული საძიებო სისტემებისთვის. მოიცავს:
- title და meta description ტეგების არსებობა
- robots.txt ხელმისაწვდომობა
- ლინკებზე აღწერითი ტექსტი
- mobile-friendly ელემენტები
- hreflang ატრიბუტები (მრავალენოვანი საიტისთვის)

### Agentic Browsing
ეს ახალი, ექსპერიმენტული კატეგორიაა. ამოწმებს რამდენად კარგად შეუძლია AI ეიჯენტს (მაგ. AI ჩატბოტს) გვერდის "წაკითხვა" და ნავიგაცია. ჯერ არ არის სტანდარტული და ჩვეულებრივ გამორთულია.

## 2.5 მოწყობილობა (Device): Mobile vs Desktop

### რატომ განსხვავდება ქულები?

Mobile ქულა თითქმის ყოველთვის **უფრო დაბალია** ვიდრე Desktop, და ეს ნორმალურია. მიზეზი ისაა, რომ Lighthouse სხვადასხვა სიმულაციას აკეთებს:

- **Mobile:**
  - CPU: 4x-ით ნელი (throttled)
  - ინტერნეტი: ნელი 4G სიმულაცია (~1.6 Mbps)
  - ეკრანის ზომა: 360x640 (პატარა)
- **Desktop:**
  - CPU: არ ანელებს
  - ინტერნეტი: შეზღუდვის გარეშე
  - ეკრანის ზომა: 1350x940

**რატომ აკეთებს ასე?** რეალურ სამყაროში მომხმარებლების დიდი ნაწილი ტელეფონიდან შედის ინტერნეტში, ხშირად ნელი კავშირით და სუსტი პროცესორით. Google-ს სურს გვერდი ამ მომხმარებლებისთვისაც იყოს სწრაფი. ამიტომ Mobile რეჟიმი ხელოვნურად ქმნის "უარეს" პირობებს — თუ ამ პირობებშიც კარგი ქულაა, ნიშნავს რომ საიტი ყველასთვის სწრაფია.

**Desktop რეჟიმი** ცოტა "ოპტიმისტურია" — ის არ ანელებს CPU-ს და ინტერნეტს, ამიტომ ქულა ბევრად მაღალია. Mobile ქულა უფრო რეალისტურ სურათს იძლევა.

## 2.6 Lighthouse-ის Performance მეტრიკები

- **FCP** (10%) — პირველი კონტენტის გამოჩენა
- **Speed Index** (10%) — ვიზუალური კონტენტის შევსების სიჩქარე
- **LCP** (25%) — ყველაზე დიდი ელემენტის გამოჩენა
- **TBT** (30%) — main thread-ის დაბლოკვის დრო
- **CLS** (25%) — layout shift-ების ჯამი

### ქულების ინტერპრეტაცია:
- **90-100:** კარგი (მწვანე)
- **50-89:** საჭიროა გაუმჯობესება (ყვითელი)
- **0-49:** ცუდი (წითელი)

## 2.7 Lighthouse ანგარიშის სექციები

### Opportunities (შესაძლებლობები):
კონკრეტული რეკომენდაციები, დაზოგილი დროის მითითებით:
- "Eliminate render-blocking resources" — 1.2s savings
- "Properly size images" — 0.8s savings
- "Remove unused JavaScript" — 0.5s savings

### Diagnostics (დიაგნოსტიკა):
დამატებითი ტექნიკური ინფორმაცია:

- **DOM-ის ზომა** — DOM (Document Object Model) არის HTML ელემენტების ხისებური სტრუქტურა. რაც მეტი ელემენტია გვერდზე (div, span, p და ა.შ.), მით მეტ მეხსიერებას და დროს მოითხოვს ბრაუზერი მათ დასარენდერებლად. თუ DOM-ში 1500+ ელემენტია, Lighthouse გაფრთხილებას აძლევს, რადგან ეს ანელებს JavaScript-ის მუშაობას, style-ების გამოთვლას და layout-ის განახლებას.

- **JavaScript Execution Time** — აჩვენებს რამდენ დროს ხარჯავს ბრაუზერი JavaScript-ის კოდის შესრულებაზე. ეს მოიცავს სკრიპტების parsing-ს (კოდის გარჩევას), compilation-ს (კომპილაციას) და execution-ს (შესრულებას). თუ ეს დრო ზედმეტად დიდია, main thread იბლოკება და მომხმარებელი ვერ ურთიერთობს გვერდთან — ვერ დააჭერს ღილაკებს, ვერ აკრეფს ტექსტს.

- **Critical Request Chains** — აჩვენებს ჩატვირთვისთვის აუცილებელი რესურსების "ჯაჭვს" (თანმიმდევრობას). მაგალითად: HTML იტვირთება → HTML-ში CSS ფაილია მითითებული → CSS იტვირთება → CSS-ში font ფაილია → font იტვირთება. ეს ჯაჭვი რაც უფრო გრძელია, მით მეტი დრო სჭირდება გვერდის სრულ ჩატვირთვას, რადგან ყოველი შემდეგი რესურსი წინას ელოდება. Lighthouse გვიჩვენებს ამ ჯაჭვებს, რომ შევამციროთ (preload, inline, lazy-load და ა.შ.).

### Passed Audits:
რა არის უკვე კარგად — ეს მნიშვნელოვანია, რომ ოპტიმიზაციისას არ გააუარესოთ.

## 2.8 მნიშვნელოვანი შენიშვნები

### რატომ Incognito რეჟიმში?
ბრაუზერის extensions-ები (მაგ. AdBlock, Grammarly, React DevTools) ჩვეულებრივ რეჟიმში ჩართულია და ისინი თავისი JavaScript კოდით ანელებენ გვერდს — ამატებენ DOM ელემენტებს, ასრულებენ სკრიპტებს, აგზავნიან request-ებს. Incognito რეჟიმში extensions-ები ნაგულისხმევად გამორთულია, ამიტომ "სუფთა" შედეგს ვიღებთ, რომელიც მხოლოდ თავად ვებგვერდის წარმადობას ასახავს.

### რატომ 3-5-ჯერ გაშვება?
Lighthouse-ის ქულა ყოველ გაშვებაზე ცოტა განსხვავდება, რადგან ბევრი ფაქტორი მერყეობს:
- ქსელის სიჩქარე შეიძლება წამიერად შეიცვალოს
- CPU-ს დატვირთვა იცვლება (სხვა პროცესები ეცილებიან)
- სერვერის response time-ი შეიძლება განსხვავდებოდეს

ერთი ტესტის შედეგი შეიძლება შემთხვევით მაღალი ან დაბალი იყოს. 3-5-ჯერ გაშვებით და საშუალოს აღებით უფრო სანდო სურათს ვიღებთ. მაგალითად: თუ სამი ტესტი მოგცეს 62, 78 და 68 — საშუალო 69 უფრო ზუსტია ვიდრე რომელიმე ცალკეული.

### Lab Data vs Field Data:
- Lighthouse აწარმოებს **ლაბორატორიულ** (lab data) ტესტებს — სიმულირებულ პირობებში, შენს კომპიუტერზე
- **Field data** (რეალური მონაცემები) — ეს არის რეალური მომხმარებლების ბრაუზერებიდან შეგროვებული სტატისტიკა (Chrome User Experience Report). როცა ნამდვილი ადამიანები სტუმრობენ საიტს, Chrome ზომავს მათ LCP-ს, CLS-ს და ა.შ. და ამ მონაცემებს Google-ში აგზავნის. Lab და Field შედეგები შეიძლება განსხვავდებოდეს, რადგან Lab სიმულაციაა, ხოლო Field — რეალობა ათასობით სხვადასხვა მოწყობილობიდან და ქსელიდან.

### სხვა რჩევები:
- დახურეთ სხვა tab-ები ტესტის დროს (CPU-ზე ზეწოლის შესამცირებლად)
