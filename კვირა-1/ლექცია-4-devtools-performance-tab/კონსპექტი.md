# ლექცია 4 — Chrome DevTools Performance Tab + პრაქტიკა

## 4.1 Performance Tab

### რა არის?
Chrome DevTools-ის Performance tab გვაძლევს ყველაზე დეტალურ სურათს იმის შესახებ, თუ რა ხდება ბრაუზერში გვერდის ჩატვირთვისა და მუშაობის დროს.

### Performance Recording:
1. გახსენით DevTools → Performance tab
2. დააჭირეთ Record (ან Cmd+E)
3. შეასრულეთ მოქმედებები გვერდზე
4. შეაჩერეთ ჩაწერა
5. გაანალიზეთ შედეგები

### Performance Tab-ის სექციები:

**Timeline Overview:**
- FPS (Frames Per Second) — მწვანე = კარგი, წითელი = frame drop
- CPU — რა ამოცანები ტვირთავს CPU-ს
- NET — ქსელის აქტივობა (როდის რა ჩამოიტვირთა: HTML, CSS, JS, სურათები, API. ლურჯი ზოლები = request-ები, სიგრძე = ჩამოტვირთვის ხანგრძლივობა. Network tab-ისგან განსხვავებით, აქ დროის ხაზზე ხედავ — JS execution-თან და Layout-თან კონტექსტში)

#### FPS (Frames Per Second) — რა არის?

FPS ნიშნავს **წამში რამდენ კადრს (ფრეიმს) ხატავს ბრაუზერი**. ბრაუზერი მუშაობს როგორც ვიდეო — ყოველ ~16.6 მილიწამში ერთ ახალ კადრს ხატავს (1000ms ÷ 60 = 16.6ms). თუ 60 კადრს ხატავს წამში (60fps) — ყველაფერი გლუვად მუშაობს: სქროლი, ანიმაციები, ინტერაქცია.

**Frame Drop (კადრის დაკარგვა)** — როცა ბრაუზერი ვერ ასწრებს 16.6ms-ში კადრის დახატვას. მაგალითად, JavaScript-ი მძიმე გამოთვლას აკეთებს და main thread-ი 200ms-ით არის "ჩაკეტილი". ამ 200ms-ის განმავლობაში ბრაუზერმა ~12 კადრი ვერ დახატა — ეს არის frame drop. **შედეგი**: სქროლი "იჭრება", ანიმაცია "ხტუნავს", გვერდი "იყინება".

Performance tab-ის ზედა ნაწილში FPS ზოლი:
- 🟩 მწვანე ზოლი = კარგი FPS (60-ს მიახლოებული)
- 🟥 წითელი ზოლი = frame drop (FPS ძალიან დაბალია)
- ზოლი რაც უფრო მაღალია, მით უკეთესი

#### "ჩაწერეთ FPS scroll-ის დროს" — რას ნიშნავს?

1. გახსენი Performance tab
2. დააჭირე Record ღილაკს
3. **დაიწყე გვერდზე სქროლი** (ზემოთ-ქვემოთ)
4. 5-10 წამის შემდეგ შეაჩერე Recording
5. ნახე FPS ზოლი — მწვანეა თუ წითელი სქროლის დროს?

თუ წითელია — სქროლის დროს რაღაც მძიმე ხდება (მაგ: scroll event-ზე JavaScript-ი ბევრ გამოთვლას აკეთებს, ან ბევრი reflow/repaint ხდება).

#### CPU ზოლი — სად არის?

CPU ზოლი არის timeline-ის ზემოთ, FPS ზოლის გვერდით (ზედა მარჯვენა კუთხეში წერია "CPU" და "NET"). ეს არის ფერადი ზოლები:
- 🟡 ყვითელი = JavaScript execution
- 🟣 იასამნისფერი = Layout / Rendering
- 🟢 მწვანე = Paint (ხატვა)
- 🔵 ლურჯი = Loading / Parse HTML

თუ CPU ზოლი სავსეა (100%) — main thread-ი გადატვირთულია და ვერ ასწრებს კადრების დახატვას.

**შენიშვნა**: Facebook-ის მსგავს რთულ საიტებზე Performance recording-ს ერევა "Profiling overhead" (თავად DevTools-ის ხარჯი), ამიტომ უმჯობესია საკუთარი პროექტით ვარჯიშობა, სადაც ფუნქციების სახელები წაკითხვადია.

---

**Main Thread:**
- ყველაზე მნიშვნელოვანი სექცია
- აჩვენებს JavaScript-ის execution-ს, layout-ს, paint-ს
- **Long Tasks** (50ms+) მონიშნულია წითელი კუთხით
- გადიდებით ხედავთ ცალკეულ ფუნქციების execution time-ს

#### Main Thread-ის გაშიფვრა (დეტალურად):

Main Thread არის ბრაუზერის "მთავარი ხაზი" — აქ ხდება ყველაფერი:
1. **JavaScript-ის შესრულება** — ფუნქციების გაშვება
2. **Layout** — ელემენტების პოზიციების გამოთვლა
3. **Paint** — პიქსელების დახატვა
4. **Event handling** — click, scroll, input მოვლენების დამუშავება

**როგორ წავიკითხოთ**: Main thread-ზე ფლეიმ ჩარტია (flame chart) — ზემოდან ქვემოთ ფუნქციების გამოძახების იერარქიაა. ზედა ზოლი = "მშობელი" ფუნქცია, ქვედა ზოლი = ფუნქცია რომელსაც ის იძახებს. ზოლის სიგანე = დრო.

**Long Task** — ნებისმიერი task რომელიც 50ms-ზე მეტ ხანს გრძელდება. მონიშნულია წითელი სამკუთხედით ზედა მარჯვენა კუთხეში. 50ms+ მნიშვნელოვანია იმიტომ, რომ 16.6ms-ში ერთი ფრეიმი უნდა დახატოს ბრაუზერმა, და 50ms = 3 ფრეიმი გაუშვა.

---

**Bottom-Up / Call Tree / Event Log:**
- Bottom-Up: რომელ ფუნქციებს სჭირდებათ ყველაზე მეტი დრო
- Call Tree: ფუნქციების გამოძახების იერარქია
- Event Log: მოვლენების ქრონოლოგიური სია

#### Bottom-Up, Call Tree, Event Log — დეტალურად:

**Bottom-Up** — "ქვემოდან ზემოთ". გიჩვენებს **რომელი ფუნქციები დახარჯეს ყველაზე მეტი დრო** (Self Time). ანუ, ყველაზე "მძიმე" ფუნქციები ზემოთ არის. აქ ხედავ:
- **Self Time** — რამდენი დრო დახარჯა თავად ამ ფუნქციამ (სხვების გამოძახების გარეშე)
- **Total Time** — Self Time + ყველა ფუნქცია რომელსაც ის იძახებს

მაგალითი: თუ `renderProducts()` 200ms-ს ხარჯავს, და მის შიგნით `formatDate()` 150ms-ს ხარჯავს — Bottom-Up-ში `formatDate()` იქნება ზემოთ 150ms Self Time-ით, რადგან ის არის ნამდვილი "დამნაშავე".

**Call Tree** — "ზემოდან ქვემოთ". გიჩვენებს **ფუნქციების გამოძახების ჯაჭვს**. ანუ, ვინ ვის გამოიძახა. ეს უფრო ხეს ჰგავს:
```
Evaluate script (907ms Total)
  └── heavyComputation (500ms)
  └── renderProducts (200ms)
       └── formatDate (150ms)
       └── DOM appendChild (50ms)
```

**Event Log** — მოვლენების ქრონოლოგიური ჩამონათვალი. აჩვენებს რა თანმიმდევრობით მოხდა მოვლენები: script evaluation, layout, paint, და ა.შ.

#### რატომ ვერ ხედავ ბევრს Facebook-ის recording-ში?

1. **Profiling overhead 95.7%** — DevTools-ის "ხარჯი" თითქმის მთელ CPU-ს ჭამს
2. **Minified კოდი** — Facebook-ის კოდში ფუნქციის სახელები `a()`, `b()` არის, არა `renderPost()`
3. **VM525:0:0** — "VM" ნიშნავს ბრაუზერის ვირტუალური მანქანა (eval() ან inline script). Chrome ასე არქმევს კოდს რომელსაც ცალკე ფაილი არ აქვს
4. **მოკლე recording** — 5-10 წამიანი ჩაწერა საჭიროა სრული სურათისთვის

**გამოსავალი**: გამოიყენე საკუთარი პროექტი (იხ. პრაქტიკა ქვემოთ), სადაც ფუნქციების სახელები კითხვადია და ხედავ რა ხდება.

### React-ში Performance Tab-ის გამოყენება:

## 4.2 Network Tab

- ფილტრაცია ტიპის მიხედვით (JS, CSS, Img, XHR)
- Throttling — ნელი ქსელის სიმულაცია
- Disable cache — ქეშის გარეშე ტესტირება
- Request/Response headers ანალიზი

### Disable Cache — რა სხვაობას იძლევა?

**Cache** — ბრაუზერი პირველად რომ ჩამოტვირთავს CSS, JS, სურათებს, ინახავს მათ ლოკალურად. მეორედ რომ გახსნი გვერდს, ეს ფაილები აღარ ჩამოიტვირთება — cache-დან წამოვა. ამიტომ მეორე ვიზიტი ყოველთვის სწრაფია.

**Disable cache ჩართული** = ყველაფერი თავიდან ჩამოიტვირთება, თითქოს პირველად ხსნი გვერდს.

**რატომ არის საჭირო?**
- ახალი მომხმარებელი პირველად რომ მოვა შენს საიტზე, cache არ ექნება
- Disable cache გაძლევს "პირველი ვიზიტის" რეალურ სურათს
- Development-ში — რომ ნახო კოდში ცვლილებები (cache-ით ძველ ვერსიას ტვირთავს)

**შენიშვნა**: Disable cache მხოლოდ მაშინ მუშაობს, როცა DevTools გახსნილია!

## 4.3 Coverage Tab

- აჩვენებს CSS/JS კოდის რამდენი პროცენტი გამოიყენება რეალურად
- წითელი = გამოუყენებელი კოდი
- გეხმარება კოდის დაყოფის (code splitting) გადაწყვეტილების მიღებაში

**როგორ გახსნათ:**
```
Cmd+Shift+P → "Coverage" → Start instrumenting coverage
```

### Coverage Tab — სად არის? (ხშირი შეკითხვა)

Coverage tab **არ არის** DevTools-ის ზედა tab-ებში (Elements, Console, Sources, Network...). ის **ცალკე უნდა გახსნა** Command Palette-ით:

1. DevTools-ში დააჭირე **Cmd+Shift+P** (Mac) ან **Ctrl+Shift+P** (Windows/Linux)
2. ჩაწერე **"Coverage"**
3. აირჩიე **"Start instrumenting coverage and reload page"**
4. Coverage panel გამოჩნდება **ქვედა ნაწილში** (Console-ის გვერდით)

Coverage panel-ში ხედავ:
- ფაილების სია (JS, CSS)
- ყოველი ფაილის **Total Bytes** და **Unused Bytes**
- პროცენტული ზოლი: 🔵 ლურჯი = გამოყენებული, 🔴 წითელი = გამოუყენებელი
- ფაილზე დაკლიკებით ხაზ-ხაზ ხედავ: მწვანე ხაზი = გამოყენებული, წითელი = არასდროს გაშვებული

**შენიშვნა**: Sources tab-ი (სადაც breakpoints და კოდი ჩანს) სხვა ინსტრუმენტია — ის კოდის debug-ისთვისაა, Coverage-ი კოდის გამოყენების ანალიზისთვის.

## 4.4 Bundle Analyzers (დამატებითი ინსტრუმენტები)

### რა არის Bundle (ბანდლი)?

როცა ვებ-აპლიკაციას ვაკეთებთ, ბევრი ცალკე ფაილი გვაქვს:
```
src/
  components/Header.js
  components/Footer.js
  pages/Home.js
  pages/Settings.js
  utils/helpers.js
```

**Bundler** (Webpack, Vite, Parcel) ამ ყველა ფაილს **აერთიანებს** ერთ ან რამდენიმე ფაილში — ამას ეწოდება **bundle**:
```
dist/
  bundle.js     ← ყველა JS ერთ ფაილში (მაგ. 500KB)
  styles.css    ← ყველა CSS ერთ ფაილში
```

ეს იმიტომ ხდება, რომ ბრაუზერისთვის 1 ფაილის ჩამოტვირთვა უფრო ეფექტურია, ვიდრე 50 ცალკე ფაილის.

**პრობლემა**: ბანდლი შეიძლება ძალიან დიდი გახდეს (2MB+), და გვჭირდება ანალიზი — რა არის შიგნით, რომელი ბიბლიოთეკა რამდენს იკავებს.

### რა არის Source Map?

Production-ში კოდი **minified** (შეკუმშული) არის:
```javascript
// ორიგინალი:
function calculateTotalPrice(items) {
  return items.reduce((sum, item) => sum + item.price, 0);
}

// minified:
function a(b){return b.reduce((c,d)=>c+d.price,0)}
```

**Source Map** (.map ფაილი) არის "რუკა", რომელიც ინახავს: minified კოდის `a` = ორიგინალის `calculateTotalPrice`. DevTools-ი ამ რუკას იყენებს debug-ისას, რომ ორიგინალი კოდი გიჩვენოს. **source-map-explorer** ამ რუკის მიხედვით ბანდლში ფაილების ზომას ანალიზებს.

### Bundle Analyzer ინსტრუმენტები:

```bash
# webpack — ბანდლის ვიზუალური რუკა (treemap)
# გიჩვენებს რომელი ბიბლიოთეკა/ფაილი რამდენ KB-ს იკავებს
npx webpack-bundle-analyzer stats.json

# vite — იგივე Vite პროექტებისთვის
npx vite-bundle-visualizer

# source-map-explorer — source map-ის მიხედვით ანალიზი
# გიჩვენებს ფაილების ზომებს ორიგინალი სახელებით
npx source-map-explorer dist/assets/*.js
```

## 4.5 Code Splitting — კოდის დაყოფა

### რა არის?

Code Splitting = ბანდლის დაყოფა ნაწილებად. ნაცვლად ერთი დიდი 2MB ფაილისა, გაყოფ რამდენიმე პატარა ფაილად (chunks), და თითოეული მხოლოდ მაშინ ჩაიტვირთება, როცა საჭიროა.

### როდის არის საჭირო?

1. **Coverage tab-ით ხედავ** რომ JS-ის 50%+ გამოუყენებელია — ეს კოდი სხვა გვერდებზეა საჭირო
2. **ბანდლი ძალიან დიდია** (500KB+) — initial load ნელია
3. **გაქვს ბევრი გვერდი/route** — მომხმარებელი ყოველთვის ყველას ვერ ნახავს
4. **მძიმე ბიბლიოთეკა** — მაგ. chart library მხოლოდ Analytics გვერდზეა საჭირო

### როგორ მუშაობს?

```javascript
// ❌ ჩვეულებრივი import — ყველაფერი ერთ ბანდლში მოხვდება
import { SettingsPage } from './pages/Settings';
import { AnalyticsPage } from './pages/Analytics';
import ChartLibrary from 'heavy-chart-library'; // 300KB!

// ✅ Dynamic import (code splitting) — ცალკე chunk-ად გამოიყოფა
// Settings-ის კოდი მხოლოდ Settings-ზე გადასვლისას ჩაიტვირთება
const SettingsPage = React.lazy(() => import('./pages/Settings'));
const AnalyticsPage = React.lazy(() => import('./pages/Analytics'));
```

### მაგალითი:

**Code splitting-ის გარეშე:**
```
bundle.js (2MB) — მთავარი გვერდის ჩატვირთვისას მთლიანი 2MB ჩამოიტვირთება
```

**Code splitting-ით:**
```
main.js (200KB)      — ჩამოიტვირთება მთავარ გვერდზე
settings.chunk.js (100KB) — ჩამოიტვირთება Settings-ზე გადასვლისას
analytics.chunk.js (500KB) — ჩამოიტვირთება Analytics-ზე გადასვლისას
```

მომხმარებელი მთავარ გვერდზე მხოლოდ 200KB ჩამოტვირთავს 2MB-ის ნაცვლად!
