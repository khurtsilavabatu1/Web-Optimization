# ლექცია 1 — რა არის Web Performance + Core Web Vitals

## 1.1 რა არის Web Performance?

Web Performance (ვებ წარმადობა) გულისხმობს იმას, თუ რამდენად სწრაფად იტვირთება ვებგვერდი, რამდენად მალე ხდება ინტერაქტიული და რამდენად გლუვად მუშაობს მომხმარებლისთვის.

### რატომ არის მნიშვნელოვანი?

- **მომხმარებლის გამოცდილება (UX):** 53% მობილური მომხმარებლებისა ტოვებენ გვერდს, თუ ის 3 წამზე მეტ ხანს იტვირთება (Google-ის კვლევა)
- **SEO რეიტინგი:** Google-ის ალგორითმი აფასებს გვერდის სიჩქარეს რანჟირების ფაქტორად
- **კონვერსია:** Amazon-ის კვლევით, ყოველი 100ms დაყოვნება 1%-ით ამცირებს გაყიდვებს
- **ხელმისაწვდომობა:** ნელი ინტერნეტის მქონე მომხმარებლები (განსაკუთრებით მობილურიდან)

### Performance Budget

Performance Budget არის ლიმიტების ნაკრები, რომელიც გუნდი ადგენს ვებგვერდის წარმადობისთვის:
- მაქსიმალური გვერდის ზომა (მაგ. 500KB)
- მაქსიმალური ჩატვირთვის დრო (მაგ. 3 წამი)
- მაქსიმალური JavaScript bundle ზომა (მაგ. 200KB gzipped)

#### რას ვეძახით „გვერდს" და როგორ იზომება მისი ზომა?

**„გვერდი"** = ყველაფერი, რაც ბრაუზერს ჩამოტვირთვა სჭირდება ერთი URL-ის გასახსნელად:
- HTML ფაილი + CSS ფაილები + JavaScript ფაილები + სურათები + ფონტები + ვიდეო + API პასუხები
- **ანუ არა მხოლოდ HTML — ყველა რესურსი, რაც Network tab-ში ჩანს**

**როგორ ვიზომავთ:**
- Chrome DevTools → Network tab → ქვედა ზოლში:
  - `transferred` — რამდენი გადმოვიდა ქსელიდან (gzip-ით შეკუმშული) — **ეს არის რეალური ტრაფიკი**
  - `resources` — რეალური ზომა მეხსიერებაში (გახსნილი)
- **500KB ლიმიტი ჩვეულებრივ `transferred`-ს გულისხმობს**

#### როგორ მოვაგვაროთ გვერდის/bundle ზომა და ჩატვირთვის დრო?

**Bundle ზომის შემცირება:**
- **Code splitting** — `React.lazy()`-ით გვერდებს ცალ-ცალკე chunk-ებად ვტვირთავთ
- **Tree shaking** — `import { orderBy } from 'lodash-es'` ნაცვლად `import _ from 'lodash'`
- **მძიმე ბიბლიოთეკების ჩანაცვლება** — `moment.js` (400KB) → `date-fns` (30KB) ან `Intl.DateTimeFormat` (0KB!)
- **გამოუყენებელი კოდის წაშლა** — DevTools Coverage tab-ით

**გვერდის ზომის შემცირება:**
- სურათების ოპტიმიზაცია (WebP, `w=600` ნაცვლად `w=3000`)
- ფონტების ოპტიმიზაცია (WOFF2, `font-display: swap`)
- Gzip/Brotli კომპრესია სერვერზე

**ჩატვირთვის დროის შემცირება:**
- Render-blocking რესურსების მოხსნა (`defer`, `async`, critical CSS inline)
- `<link rel="preconnect">` მნიშვნელოვან domain-ებთან
- Lazy loading (`loading="lazy"`)

### ვებგვერდის ჩატვირთვის პროცესი:
```
1. DNS Lookup      → დომენის IP მისამართზე გადაყვანა
2. TCP Connection  → სერვერთან კავშირის დამყარება
3. TLS Handshake   → HTTPS უსაფრთხო კავშირი
4. HTTP Request    → HTML-ის მოთხოვნა
5. Server Response → სერვერი აბრუნებს HTML-ს (TTFB)
6. HTML Parsing    → ბრაუზერი კითხულობს HTML-ს
7. CSS/JS Loading  → დამატებითი რესურსების ჩატვირთვა
8. Rendering       → გვერდის ვიზუალური აგება
9. Interactive     → JavaScript-ის შესრულება, გვერდი მზადაა
```

## 1.2 Core Web Vitals

Google-ის მიერ განსაზღვრული სამი ძირითადი მეტრიკა, რომელიც ზომავს მომხმარებლის რეალურ გამოცდილებას:

### LCP — Largest Contentful Paint
- **რა ზომავს:** რამდენ ხანს სჭირდება გვერდის ყველაზე დიდი ელემენტის გამოჩენას (სურათი, ვიდეო, ტექსტის ბლოკი)
- **კარგი:** < 2.5 წამი
- **საშუალო:** 2.5 - 4.0 წამი
- **ცუდი:** > 4.0 წამი
- **რა აუარესებს:** ნელი სერვერის პასუხი, render-blocking რესურსები, ნელი რესურსების ჩატვირთვა, client-side rendering

#### თუ LCP ცუდია ან საშუალოა — რას ვაკეთებთ?

**ნაბიჯი 1:** გაარკვიეთ რომელი ელემენტია LCP → DevTools → Performance → Timings → LCP-ზე დაკლიკება

**ნაბიჯი 2:** გამოასწორეთ:

| მიზეზი | გადაწყვეტა |
|--------|-----------|
| ნელი სერვერი (TTFB > 600ms) | CDN, SSG — **ბექენდის პრობლემაა** |
| Render-blocking CSS/JS | Critical CSS inline, `<script defer>` |
| დიდი LCP სურათი | `<link rel="preload" as="image">`, WebP, ზომის შემცირება |
| LCP ტექსტია + ფონტი ნელა | `font-display: swap`, font preload |
| Client-side rendering | SSR/SSG-ზე გადასვლა (Next.js) |

#### ნელი სერვერის პასუხი — ბექის ბრალია?

**დიახ, ძირითადად ბექენდის პასუხისმგებლობაა** (ნელი DB, არაეფექტური API, ნელი SSR).
**ფრონტენდს რა შეუძლია:** `<link rel="preconnect">`, Service Worker cache, SSG, და **ბექენდ გუნდთან კომუნიკაცია**.

#### რა არის Render-blocking რესურსები?

ფაილები, რომლებიც ბრაუზერს აჩერებენ გვერდის დახატვაში:
- **CSS** — ყოველთვის blocking-ია. გადაწყვეტა: critical CSS inline, არა-კრიტიკული async
- **JS** — blocking-ია `defer`/`async` გარეშე. გადაწყვეტა: `<script defer>`

```html
<!-- ❌ Render-blocking -->
<script src="app.js"></script>
<link rel="stylesheet" href="huge.css">

<!-- ✅ არ ბლოკავს -->
<script src="app.js" defer></script>
<link rel="stylesheet" href="non-critical.css" media="print" onload="this.media='all'">
```

#### რა არის Client-Side Rendering (CSR) და რატომ აუარესებს?

**CSR** = სერვერი აბრუნებს ცარიელ HTML-ს (`<div id="root"></div>`), JavaScript ბრაუზერში ქმნის კონტენტს.

```
CSR:  ცარიელი HTML → JS ჩამოტვირთვა (300KB+) → Parse → Execute → Render → LCP! (ნელი)
SSR:  მზა HTML → LCP! (სწრაფი) → JS ჩამოტვირთვა → Hydration → ინტერაქტიული
```

მომხმარებელი CSR-ით ხედავს ცარიელ ეკრანს სანამ JS არ ჩაიტვირთება, არ დაიპარსება და არ შესრულდება.

### INP — Interaction to Next Paint (FID-ის მემკვიდრე)
- **რა ზომავს:** რამდენ ხანს სჭირდება გვერდს მომხმარებლის ინტერაქციაზე რეაგირება (click, tap, keypress)
- **კარგი:** < 200ms
- **საშუალო:** 200 - 500ms
- **ცუდი:** > 500ms
- **რა აუარესებს:** მძიმე JavaScript ამოცანები main thread-ზე, long tasks

#### რატომ არ ხდება წამიერი რეაგირება?

**Main thread** = ბრაუზერის ერთადერთი ძაფი, რომელიც ასრულებს JavaScript-ს, ხატავს UI-ს, ამუშავებს click/scroll/keypress მოვლენებს. **ეს ყველაფერი ერთ რიგში დგას!**

თუ main thread-ზე მძიმე JavaScript სრულდება, მომხმარებლის click ელოდება რიგში — ვერ რეაგირებს.

#### რა არის Long Task?

**Long Task** = ნებისმიერი ამოცანა, რომელიც main thread-ს **50ms-ზე მეტხანს** იკავებს. ამ დროს ბრაუზერი „გაყინულია".

DevTools → Performance tab-ში Long Tasks მონიშნულია **წითელი კუთხით**.

#### მძიმე ამოცანების კონკრეტული მაგალითები main thread-ზე:

| მაგალითი | რამდენ ხანს ბლოკავს | გადაწყვეტა |
|----------|-------------------|-----------|
| 1000 პროდუქტის სორტირება + ფილტრაცია ყოველ keystroke-ზე | 100-300ms | `debounce(300ms)` — 300ms პაუზის შემდეგ |
| 1000 DOM ელემენტის ერთდროულად შექმნა | 100-200ms | Pagination (50 row ერთდროულად) ან Virtualization |
| Third-party სკრიპტები (Analytics, Facebook, Chat widget) | 50-200ms თითო | `async` ატრიბუტი, lazy load |
| დიდი JSON-ის parsing (10MB) | 200ms+ | Web Worker-ში გადატანა |
| მძიმე ციკლი (10M iteration) | 200-500ms | Web Worker ან ამოცანის დაყოფა `requestIdleCallback`-ით |

```javascript
// ❌ Long Task — ყოველ keystroke-ზე
searchInput.addEventListener('input', () => {
    products.filter(...).sort(...);  // 200ms — main thread ბლოკირებულია!
    renderAllRows();                 // 100ms — კიდევ ბლოკირებულია!
});

// ✅ გადაწყვეტა — debounce
searchInput.addEventListener('input', debounce(() => {
    products.filter(...).sort(...);
    renderVisibleRows(50);  // მხოლოდ 50 row
}, 300));
```

### CLS — Cumulative Layout Shift
- **რა ზომავს:** ვიზუალური სტაბილურობა — რამდენად „ხტება" კონტენტი ჩატვირთვისას
- **კარგი:** < 0.1
- **საშუალო:** 0.1 - 0.25
- **ცუდი:** > 0.25
- **რა აუარესებს:** ზომების გარეშე სურათები, დინამიურად ჩასმული კონტენტი, late-loading ფონტები

#### Late-loading ფონტები — როდის გვაქვს და რატომ იწვევს CLS-ს?

**Late-loading ფონტი** = ბრაუზერი ჯერ system font-ით აჩვენებს ტექსტს, მერე custom font ჩამოიტვირთება და ტექსტის ზომა/spacing იცვლება → კონტენტი „გადახტება" = **layout shift!**

```css
/* ❌ font-display: block — ტექსტი უჩინარია სანამ ფონტი ჩაიტვირთება */
@font-face {
  font-family: 'MyFont';
  src: url('myfont.woff2');
  font-display: block;
}

/* ✅ font-display: swap — ჯერ system font ჩანს, ფონტის ჩატვირთვის შემდეგ შეიცვლება */
@font-face {
  font-family: 'MyFont';
  src: url('myfont.woff2');
  font-display: swap;
}
```

**CLS-ის ყველა მიზეზი და გადაწყვეტა:**

| მიზეზი | გადაწყვეტა |
|--------|-----------|
| `<img>` width/height ატრიბუტების გარეშე | ყოველთვის მიუთითეთ `width` და `height` |
| ბანერი/რეკლამა დინამიურად ჩაისმება | `min-height` container-ზე — ადგილის დაჯავშნა |
| ფონტი ცვლის ტექსტის ზომას | `font-display: swap` + ფონტის preload |
| iframe ზომის გარეშე | `width` და `height` ატრიბუტები |

### დამატებითი მეტრიკები:

#### FCP (First Contentful Paint) — პირველი კონტენტის გამოჩენა
წამი, როცა ბრაუზერი ეკრანზე **პირველად ხატავს რაიმეს** — ტექსტს, სურათს, SVG-ს ან canvas-ს. ცარიელი ფონი არ ითვლება. ეს არის მომენტი, როცა მომხმარებელი ხვდება: „გვერდი იტვირთება, რაღაც ხდება."
- **კარგი:** < 1.8 წამი
- **ცუდი:** > 3.0 წამი

#### TBT (Total Blocking Time) — main thread-ის დაბლოკვის ჯამური დრო
FCP-სა და Interactive-ს შორის, ყველა Long Task-ის (50ms+) **50ms-ს ზემოთ** დროის ჯამი.

მაგალითი: task 150ms → blocking time = 150 - 50 = **100ms**. სამი ასეთი task → TBT = **300ms**.

**რა ბლოკავს main thread-ს (კონკრეტული მაგალითებით):**

**1. JavaScript-ის parse/compile/execute:**
```javascript
// ❌ მძიმე ციკლი — 200-500ms ბლოკავს
for (let i = 0; i < 10000000; i++) {
    result += Math.sqrt(i);
}

// ❌ 1000 პროდუქტის ფილტრაცია + სორტირება ყოველ keystroke-ზე
products.filter(...).sort(...).map(...)  // 100-300ms
```

**2. Layout/Reflow — DOM-ის ხელახალი გამოთვლა:**
```javascript
// ❌ ელემენტის ზომა/პოზიცია იცვლება → ბრაუზერი ხელახლა ითვლის ყველა ელემენტს
element.style.width = '500px';
parent.appendChild(newElement);
element.remove();

// ❌ Forced Reflow — ზომის წაკითხვა ცვლილების შემდეგ
element.style.width = '500px';
console.log(element.offsetHeight); // ← აიძულებს ბრაუზერს ახლავე გამოთვალოს!

// ❌ 1000 ელემენტის ჩასმა loop-ში = 1000 layout!
for (let i = 0; i < 1000; i++) {
    tbody.appendChild(createRow(i));
}

// ✅ innerHTML ერთი assignment — 1 layout
tbody.innerHTML = rows.join('');
```

**3. Style recalculation — CSS-ის ხელახალი გამოთვლა:**
```javascript
// ❌ კლასის დამატება/წაშლა → ბრაუზერი ხელახლა ითვლის რომელი CSS ვის ეხება
element.classList.add('active');
element.style.color = 'red';

// ❌ CSS ფაილის დინამიურად ჩამატება
document.head.appendChild(styleElement);
```

**4. Third-party scripts (analytics, ads, chat widgets):**
```html
<!-- ❌ Google Analytics, Facebook Pixel, Intercom — თითოეული 50-200ms -->
<script src="https://www.google-analytics.com/analytics.js"></script>
<script src="https://connect.facebook.net/en_US/fbevents.js"></script>

<!-- ✅ async ატრიბუტით — main thread-ს არ ბლოკავს ჩატვირთვისას -->
<script src="https://www.google-analytics.com/analytics.js" async></script>
```

#### TTFB (Time to First Byte) — სერვერის პასუხის დრო
დრო ბრაუზერის მოთხოვნიდან სერვერიდან **პირველი ბაიტის** მიღებამდე. მოიცავს: DNS lookup + TCP connection + TLS + სერვერის processing.
- **კარგი:** < 200ms
- **ცუდი:** > 600ms
- **ძირითადად ბექენდის პასუხისმგებლობაა** — ფრონტენდს შეუძლია preconnect, caching, SSG

#### Speed Index
რამდენად სწრაფად ივსება ვიზუალური კონტენტი
