## Leak #1 — გაუწმენდავი event listener + არასწორი dependency

**ფაილი:** `src/components/ResizeWidget.jsx`

```jsx
// ❌ before
useEffect(() => {
  const handleResize = () => {
    setSize({ width: window.innerWidth, height: window.innerHeight })
    setEvents(previous => previous + 1)
  }

  console.log('📐 resize listener დაემატა')
  window.addEventListener('resize', handleResize)
}, [size])                          // cleanup არ არის + dependency იცვლება

// ✅ after
useEffect(() => {
  const handleResize = () => {
    setSize({ width: window.innerWidth, height: window.innerHeight })
    setEvents(previous => previous + 1)
  }

  window.addEventListener('resize', handleResize)
  return () => window.removeEventListener('resize', handleResize)
}, [])                              // size-ზე დამოკიდებულება საჭირო არ არის
```

**ორი დეფექტი:** (1) `return () => window.removeEventListener(...)` არ არის;
(2) dependency მასივში `size`-ია, ხოლო effect-ს `size` არ სჭირდება (setSize მხოლოდ წერს) —
ამიტომ ყოველ რენდერზე ახალი listener ემატება.

**მოსალოდნელი რიცხვები (ფანჯრის ნაბიჯობრივი, ცალკეული ცვლილებები):**

| ცვლილება # | listeners (ვიჯეტის) | „დაფიქსირებული მოვლენა" |
|---|---|---|
| 0 (mount) | 1 | 0 |
| 1 | 2 | 1 |
| 2 | 3 | 3 |
| 3 | 4 | 6 |
| 4 | 5 | 10 |
| 5 | 6 | 15 |
| 6 | 7 | 21 |

**რატომ იზრდება „მოვლენა" ერთზე მეტით:** ერთი `resize` მოვლენა **ყველა** მიბმულ
handler-ს იძახებს. თუ 3 listener-ია, ერთი ცვლილება = 3 გამოძახება = `+3`. React ამ სამ
`setState`-ს ერთ რენდერში აერთიანებს (batching), ამიტომ listeners მხოლოდ `+1`-ით იზრდება.
შედეგი — „მოვლენების" სამკუთხა ზრდა (1, 3, 6, 10, 15, 21).

> ფანჯრის **გაწევით** (drag) ზომის ცვლილება ათობით `resize` მოვლენას ტოვებს, ამიტომ
> რიცხვები გაცილებით სწრაფად იზრდება. სტუდენტს ურჩიეთ ნაბიჯობრივი ცვლილება
> (ან ფანჯრის „მიკვრა" ეკრანის ნახევარზე), რომ ცხრილი შედარებადი გამოვიდეს.

**unmount-ის შემდეგ:** listeners **არ** მცირდება — ეს არის leak-ის მთავარი მტკიცებულება.
გასწორების შემდეგ unmount-ზე ბრუნდება საწყის მნიშვნელობაზე.

**კითხვის პასუხი:** `useEffect`-ის cleanup არის ერთადერთი ადგილი, სადაც React
გარანტირებულად შეგატყობინებთ, რომ კომპონენტი ქრება. ყველაფერი, რაც კომპონენტის
„გარეთ" დარეგისტრირდა (window/document listener, timer, subscription, observer,
WebSocket), React-ისთვის უხილავია და თავად არ იშლება.

## Leak #2 — გაუწმენდავი `setInterval`

**ფაილი:** `src/components/ServerMonitor.jsx` (პირველი `useEffect`)

```jsx
// ❌ before
useEffect(() => {
  setInterval(() => {
    setTicks(previous => previous + 1)
    console.log('⏱ tick', ...)
  }, 1000)
}, [])

// ✅ after
useEffect(() => {
  const intervalId = setInterval(() => {
    setTicks(previous => previous + 1)
    console.log('⏱ tick', ...)
  }, 1000)

  return () => {
    console.log('⏹ მონიტორინგის ინტერვალი შეჩერდა')
    clearInterval(intervalId)
  }
}, [])
```

**მოსალოდნელი რიცხვები:** 5 ჩართვა/გამორთვის შემდეგ + 6-ე ჩართვა = **6 პარალელური
ინტერვალი** → `⏱ tick` 5 წამში ≈ **30-ჯერ**, „tick: N" მრიცხველი 5 წამში **+30**
(ანუ წამში 6-ით, არა 1-ით). unmount-ის შემდეგ ლოგები **არ** ჩერდება.

**შენიშვნა:** `setTicks` unmount-ის შემდეგ „დაკარგულ" state-ზე იწერება — React 18-ში ეს
გამაფრთხილებელს აღარ იწვევს (წინა ვერსიებში იყო *"Can't perform a React state update on
an unmounted component"*). სწორედ ამიტომ არის Console-ის ლოგები და Performance Monitor
ერთადერთი საიმედო მტკიცებულება.

**კითხვის პასუხი:** გაუწმენდავი ინტერვალი ჩვეულებრივ პატარა მეხსიერებას იჭერს (callback
+ მისი closure: `setTicks`, კომპონენტის scope), ამიტომ JS Heap-ზე მკვეთრი ზრდა არ ჩანს.
ნამდვილი ზიანი — **CPU-ს უსაქმური ხარჯვა**, ბატარეა, და closure-ით შენახული მთელი
კომპონენტის scope, რომელიც GC ვერ ათავისუფლებს.

## Leak #3 — Async პასუხების რბოლა (race condition)

**ფაილი:** `src/components/ServerMonitor.jsx` (მეორე `useEffect`)

```jsx
// ❌ before
useEffect(() => {
  setLoading(true)
  fetchServerMetrics(serverId).then(data => {
    setMetrics(data)
    setLoading(false)
  })
}, [serverId])

// ✅ after
useEffect(() => {
  const controller = new AbortController()
  setLoading(true)

  fetchServerMetrics(serverId, { signal: controller.signal })
    .then(data => {
      setMetrics(data)
      setLoading(false)
    })
    .catch(error => {
      if (error.name === 'AbortError') {
        console.log('⏹ მოთხოვნა გაუქმდა:', serverId)
        return
      }
      console.error(error)
      setLoading(false)
    })

  return () => controller.abort()
}, [serverId])
```

**დროის ღერძი (srv-1 → მაშინვე srv-2):**

```
0 ms     📡 მოთხოვნა srv-1 (დაბრუნდება 2000 ms-ზე)
~50 ms   📡 მოთხოვნა srv-2 (დაბრუნდება 400 ms-ზე)  ← პირველი effect არ გაუქმებულა
450 ms   📥 srv-2 → პანელი აჩვენებს srv-2-ს  ✅
2000 ms  📥 srv-1 → პანელი გადაეწერა srv-1-ით  ❌
```

**შედეგი:** select-ში „არჩეულია srv-2 · Tbilisi", პანელში კი „ნაჩვენები მონაცემები:
srv-1 · Frankfurt". ეს არის კლასიკური race condition.

**კითხვის პასუხები:**

- **რითი განსხვავდება:** აქ მეხსიერების ზრდა თითქმის არ არის — ზიანი **სისწორისაა**:
  მომხმარებელს ეჩვენება არასწორი მონაცემი. ეს ყველაზე საშიში ტიპია, რადგან „მეხსიერების
  გრაფიკი ნორმალურია" და პრობლემა უხილავია მონიტორინგისთვის.
- **flag vs AbortController:** `let cancelled = true` მხოლოდ **შედეგს** აგდებს, მოთხოვნა
  კი სრულდება (ქსელი და სერვერი მაინც იხარჯება). `AbortController` ნამდვილად **წყვეტს**
  მოთხოვნას. flag-ი მისაღები მინიმუმია, როცა API abort-ს არ უჭერს მხარს.

## Leak #4 — უსასრულოდ მზარდი ბუფერი

**ფაილი:** `src/components/LogFeed.jsx`

```jsx
// ❌ before
const LOG_BUFFER = []               // მოდულის დონეზე — unmount-ის შემდეგაც ცოცხალია

const entry = {
  ts, level, message,
  payload: new Array(20_000).fill('log-payload-chunk'),   // ~160 KB ერთ ჩანაწერზე
}
LOG_BUFFER.push(entry)              // არასოდეს იჭრება

// ✅ after — ვარიანტი 1 (ბუფერი რჩება, მაგრამ შეზღუდულია)
const MAX_BUFFER = 200

const entry = { ts, level, message }          // payload საერთოდ არ გვჭირდება
LOG_BUFFER.push(entry)
if (LOG_BUFFER.length > MAX_BUFFER) {
  LOG_BUFFER.splice(0, LOG_BUFFER.length - MAX_BUFFER)
}

// ✅ after — ვარიანტი 2 (სუფთა React-ული)
setLines(previous => [...previous, entry].slice(-8))
// LOG_BUFFER საერთოდ ამოღებულია
```

**მოსალოდნელი რიცხვები (before):** ერთი ჩანაწერი ≈ 160 KB, 300 ms-ში 1 ჩანაწერი
≈ **0.5 MB/წმ** → 30 წამში JS heap **+10-20 MB**, „ბუფერი: N" = **~100**.
`Collect garbage`-ის შემდეგ მეხსიერება **არ** ბრუნდება.

**after:** 30 წამში heap-ის ზრდა < 1-2 MB, ბუფერი ≤ 200, unmount + GC → ბრუნდება საწყისზე.

**კითხვის პასუხი:** GC ათავისუფლებს მხოლოდ იმას, რაზეც აღარ არსებობს **მიღწევადი
რეფერენსი**. `LOG_BUFFER` მოდულის დონეზეა გამოცხადებული — ანუ მოდულის სიცოცხლის ბოლომდე
(= გვერდის დახურვამდე) ცოცხალია და თავის ყველა ელემენტს იჭერს. კომპონენტის unmount-ს
ამასთან არავითარი კავშირი აქვს.

## Leak #5 — Detached DOM

**ფაილი:** `src/components/ChartWidget.jsx`

```jsx
// ❌ before
const renderedBars = []                     // მოდულის დონეზე „ქეში"

while (host.firstChild) {
  renderedBars.push(host.firstChild)        // ← ამოღებულ ელემენტს ვინახავთ
  host.removeChild(host.firstChild)
}

// ✅ after
host.replaceChildren()                      // ან: while (host.firstChild) host.removeChild(host.firstChild)
// renderedBars საერთოდ ამოღებულია (ან cleanup-ში: renderedBars.length = 0)
```

**მოსალოდნელი რიცხვები:** 40 ელემენტი × 2 კადრი/წმ = **80 კვანძი/წმ** →
DOM Nodes 10 წამში **+~800**, 20 წამში **+~1600**. ეკრანზე ყოველთვის მხოლოდ 40 ზოლია.

**Heap Snapshot (ფილტრი „Detached"):** `Detached HTMLDivElement` ≈ 1600 ცალი,
Retained Size რამდენიმე MB. **Retainers** სექცია აჩვენებს, რომ მათ `renderedBars`
მასივი იჭერს — ეს არის ამ სავარჯიშოს გადამწყვეტი მომენტი (სტუდენტმა ცვლადის სახელი
snapshot-იდან უნდა წაიკითხოს, არა კოდიდან).

**კითხვის პასუხები:**

- **detached DOM** — ელემენტი, რომელიც დოკუმენტის ხიდან ამოღებულია (`removeChild`), მაგრამ
  JavaScript-ის კოდი კვლავ ინახავს მასზე რეფერენსს. ეკრანზე არ ჩანს, მეხსიერებას კი იჭერს —
  თავის ატრიბუტებით, `dataset`-ით, style-ით და შვილებითაც.
- **React-ის რენდერით:** ასეთი leak-ი არ მოხდებოდა — React თავად აშორებს ელემენტებს და
  რეფერენსებს არ ინახავს. leak-ი შესაძლებელი გახდებოდა, თუ ჩვენ თვითონ შევინახავდით
  DOM კვანძებს `useRef`-ში ან გარე მასივში. ზოგადი წესი: **DOM API-თ ხელით მუშაობა
  React-ში memory leak-ების ყველაზე ხშირი წყაროა.**

## პრობლემა #6 — Error Boundary

### 7.1 დიაგნოზი

**ფაილი:** `src/components/ErrorBoundary.jsx`

```jsx
// ❌ before
componentDidCatch(error, errorInfo) {
  console.error('🚨 ErrorBoundary:', error.message)
  this.setState({ error })         // state იწერება...
}

render() {
  return this.props.children       // ...მაგრამ render მას არ კითხულობს
}
```

**რა ხდება სინამდვილეში:**

1. `CrashPanel` render-ში კითხულობს `incident.severity`-ს, სადაც `incident = null` →
   `TypeError: Cannot read properties of null`
2. boundary იჭერს შეცდომას, `componentDidCatch` ილოგება (`🚨 ErrorBoundary` **ჩანს**,
   componentStack-იც ჩანს) — ანუ boundary „მუშაობს"
3. `setState`-ის შემდეგ boundary ხელახლა რენდერდება და **ისევ `children`-ს** აბრუნებს
4. `crashMode` `App`-ის state-შია და არ შეცვლილა → `CrashPanel` ისევ იგდებს შეცდომას
5. React ხედავს, რომ იმავე boundary-ში შეცდომა გამეორდა, უარს ამბობს აღდგენაზე და
   შეცდომას root-მდე ატანს → **მთელი ხე unmount-დება = თეთრი ეკრანი**

Console-ში ამ დროს ჩანს React-ის შეტყობინებაც: *"The above error occurred in the
&lt;CrashPanel&gt; component"* და შემდეგ — *"Consider adding an error boundary..."*.

**ორი დეფექტი:** (1) აკლია `static getDerivedStateFromError(error)` — სწორედ ის
ამბობს React-ს, **რა მდგომარეობაში** გადავიდეს შეცდომის დროს (render-ის ფაზაში);
(2) `render()` არ ამოწმებს `this.state.error`-ს, ანუ fallback არსად არ ბრუნდება.

**რატომ არ კმარა `componentDidCatch`:** ის commit-ის ფაზაში იძახება და მისი დანიშნულებაა
**ლოგირება** (Sentry, LogRocket). *რა ვაჩვენოთ* — ეს render-ის ფაზის გადაწყვეტილებაა,
ამიტომ `getDerivedStateFromError` არსებობს. (ისტორიულად `componentDidCatch`+`setState`
მუშაობდა, მაგრამ მაინც სავალდებულოა, რომ `render` ამ state-ს **წაიკითხოს**.)

### 7.2 გამოსწორება

```jsx
// ✅ after
export default class ErrorBoundary extends Component {
  constructor(props) {
    super(props)
    this.state = { error: null }
  }

  static getDerivedStateFromError(error) {
    return { error }
  }

  componentDidCatch(error, errorInfo) {
    console.error('🚨 ErrorBoundary:', error.message)
    console.error('კომპონენტების ჯაჭვი:', errorInfo.componentStack)
    // რეალურ პროექტში: Sentry.captureException(error, { extra: errorInfo })
  }

  handleRetry = () => {
    this.setState({ error: null })
    this.props.onReset?.()        // ← შეცდომის მიზეზის მოშორება
  }

  render() {
    if (this.state.error) {
      return (
        <div className="boundary-fallback">
          <h2>რაღაც შეცდომა მოხდა</h2>
          <p className="mono">{this.state.error.message}</p>
          <button className="btn btn-primary btn-sm" onClick={this.handleRetry}>
            ხელახლა ცდა
          </button>
        </div>
      )
    }

    return this.props.children
  }
}
```

**რატომ არ კმარა `setState({ error: null })`:** შეცდომის **მიზეზი** boundary-ს გარეთაა —
`App`-ის `crashMode` კვლავ `'render'`-ია. boundary-ს state-ის გასუფთავებაზე `CrashPanel`
ხელახლა დარენდერდება, ისევ დაეცემა და fallback-ი მაშინვე დაბრუნდება (ან ეკრანი
გათეთრდება). ამიტომ `onReset`-ის (`() => setCrashMode(null)`) გამოძახება აუცილებელია.
ეს არის რეალური პროექტების მთავარი გაკვეთილი: **retry უნდა გაასუფთაოს მიზეზი, არა მხოლოდ ნიშანი.**

### 7.3 Boundary-ების გრანულარობა

ერთი boundary-ს დროს render-ის შეცდომა **ყველა** ვიჯეტს ანადგურებს — „ლაივ ლოგიც" და
„გრაფიკიც" ქრება (და მათი ინტერვალებიც cleanup-ით ჩერდება, თუ #2/#4/#5 გასწორებულია).

```jsx
// ✅ after (App.jsx)
{showMonitor && <ErrorBoundary><ServerMonitor serverId={serverId} /></ErrorBoundary>}
{showResize && <ErrorBoundary><ResizeWidget /></ErrorBoundary>}
{showLogs && <ErrorBoundary><LogFeed /></ErrorBoundary>}
{showChart && <ErrorBoundary><ChartWidget /></ErrorBoundary>}
<ErrorBoundary onReset={() => setCrashMode(null)}>
  <CrashPanel crashMode={crashMode} onCrash={setCrashMode} />
</ErrorBoundary>
```

მისაღებია გარე boundary-ს შენარჩუნებაც (ორი დონე: „მთელი აპი" + „ცალკე სექციები") —
ეს სწორედ ისაა, რასაც რეალურ პროექტებში აკეთებენ.

### 7.4 რას ვერ იჭერს boundary

| ღილაკი | fallback? | Console | დაიჭირა? |
|---|---|---|---|
| 💥 render-ის შეცდომა | დიახ (გასწორების შემდეგ) | `🚨 ErrorBoundary` + componentStack | **დიახ** |
| ⚠️ handler-ის შეცდომა | არა | `Uncaught TypeError: Cannot read properties of null (reading 'threshold')` | არა |
| ⏳ async შეცდომა | არა | `Uncaught TypeError: Cannot read properties of undefined (reading 'lines')` (500 ms-ის შემდეგ) | არა |

**რატომ:** Error Boundary იჭერს მხოლოდ იმ შეცდომებს, რომლებიც **React-ის render/lifecycle
ფაზაში** ხდება. event handler და `setTimeout` React-ის რენდერის ციკლის **გარეთ**, ბრაუზერის
სხვა task-ში სრულდება — მათი გადაგდებული შეცდომა `window.onerror`-მდე მიდის, boundary-მდე — არა.

```jsx
// ✅ after (CrashPanel.jsx)
const [localError, setLocalError] = useState(null)

const handleHandlerCrash = () => {
  try {
    const config = null
    console.log('ზღვარი:', config.threshold)
  } catch (error) {
    console.error('handler-ის შეცდომა:', error.message)
    setLocalError('პარამეტრები ვერ ჩაიტვირთა. სცადეთ განახლება.')
  }
}

const handleAsyncCrash = () => {
  setTimeout(() => {
    try {
      const report = undefined
      console.log('ანგარიში:', report.lines.length)
    } catch (error) {
      setLocalError('ანგარიშის მიღება ვერ მოხერხდა.')
    }
  }, 500)
}

// render-ში:
{localError && <div className="alert alert-error">{localError}</div>}
```

**კითხვების პასუხები:**

- **რატომ class:** `getDerivedStateFromError` და `componentDidCatch` მხოლოდ class
  კომპონენტის lifecycle მეთოდებია — hooks-ის ექვივალენტი React-ს დღემდე არ აქვს.
  პრაქტიკაში ხშირად `react-error-boundary` ბიბლიოთეკას იყენებენ, რომელიც შიგნით
  სწორედ class boundary-ს ახვევს.
- **3 ყველაზე ხშირი რეალური მიზეზი:** (1) API-ს პასუხი მოსალოდნელისგან განსხვავებულია
  (`undefined`-ის property-ს წაკითხვა); (2) `null`/`undefined` state, სანამ მონაცემები
  ჩაიტვირთება (loading state-ის არარსებობა); (3) ობიექტის ან მასივის პირდაპირ რენდერი
  / არასწორი ტიპი props-ში.
