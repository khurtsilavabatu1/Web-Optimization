## პრობლემა #1 — `response.ok` არ მოწმდება

**ფაილები:** `src/utils/api.js` → `loadJson`, `src/components/ApiPanel.jsx`

```js
// ❌ before (api.js)
export async function loadJson(url) {
  const response = await fetch(url, { headers: { Accept: 'application/json' } })
  const text = await response.text()

  let data = []
  try {
    data = JSON.parse(text)
  } catch {
    data = []            // ← შეცდომას „ყლაპავს"
  }

  return { data, status: response.status, statusText: response.statusText, ms }
}

// ✅ after
export async function loadJson(url) {
  const response = await fetch(url, { headers: { Accept: 'application/json' } })

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText || 'მოთხოვნა ჩავარდა'}`)
  }

  const data = await response.json()   // ვალიდური JSON აქ აუცილებელია
  return { data, status: response.status, statusText: response.statusText, ms }
}
```

```jsx
// ❌ before (ApiPanel.jsx)
const response = await loadJson(url)
setResult({ ...response, url, label })
setError(null)                          // ყოველთვის null
...
<span className="chip chip-ok">წარმატება</span>   // hardcoded

// ✅ after
try {
  const response = await loadJson(url)
  setResult({ ...response, url, label })
  setError(null)
} catch (requestError) {
  setResult(null)
  setError(requestError.message)
} finally {
  setLoading(false)
}
...
<span className={result.status < 400 ? 'chip chip-ok' : 'chip chip-error'}>
  {result.status < 400 ? 'წარმატება' : 'შეცდომა'}
</span>
```

**მოსალოდნელი ცხრილი (გასწორებამდე):**

| ღილაკი | URL | Status | გვერდზე | ჩანაწერი |
|---|---|---|---|---|
| ტიკეტების ჩატვირთვა | `/tickets.json` | 200 | წარმატება | 8 |
| არქივის ჩატვირთვა | `/tickets-archive.json` | **404** | **წარმატება** ❌ | 0 |

**Response tab-ში 404-ზე:** Vite dev სერვერი ტექსტს/HTML-ს აბრუნებს, არა JSON-ს — სწორედ
ამიტომ `JSON.parse` ჩავარდება და `catch` ცარიელ მასივს აბრუნებს.

**კითხვის პასუხი:** `fetch()` Promise-ს **მხოლოდ ქსელის შეცდომაზე** reject-ავს (DNS,
გათიშული ინტერნეტი, CORS-ის ბლოკი). 404/500 სრულიად ვალიდური HTTP პასუხია — `fetch`
წარმატებით სრულდება. სტატუსის შემოწმება დეველოპერის პასუხისმგებლობაა (`response.ok`).

**`JSON.parse`-ის catch:** ცარიელი მასივის დაბრუნება „წარმატებას" აყალბებს. მართებულია
შეცდომის გადაგდება (`throw new Error('პასუხი არ არის ვალიდური JSON')`) — მონაცემების
არარსებობა და მონაცემების „0 ცალი" სხვადასხვა მდგომარეობაა.

**შენიშვნა `Accept` header-ზე:** `loadJson` განზრახ აგზავნის `Accept: application/json`-ს —
ამის გარეშე Vite dev სერვერი არარსებულ ფაილზე SPA fallback-ს (index.html, სტატუსი **200**)
აბრუნებდა და 404 არ რეპროდუცირდებოდა. თუ სტუდენტი ამ header-ს წაშლის, სიმპტომი გაქრება —
ეს კარგი საბაბია იმის განხილვად, რომ dev სერვერის ქცევა და production სერვერის ქცევა ერთი არ არის.

## პრობლემა #2 — არასტაბილური dependency → request-ების ნაკადი

**ფაილი:** `src/components/ApiPanel.jsx`

```jsx
// ❌ before
const searchOptions = { term: serverTerm, limit: 5 }   // ახალი ობიექტი ყოველ რენდერზე

useEffect(() => {
  if (!liveSearch) return
  loadJson(`/tickets.json?q=${...}`).then(response => {
    setLiveRows(...)
    setRequestCount(count => count + 1)                // → render → ახალი searchOptions → effect
  })
}, [liveSearch, searchOptions])

// ✅ after
useEffect(() => {
  if (!liveSearch) return

  const controller = new AbortController()
  const timer = setTimeout(() => {
    loadJson(`/tickets.json?q=${encodeURIComponent(serverTerm)}&limit=5`)
      .then(response => {
        setLiveRows(Array.isArray(response.data) ? response.data.length : 0)
        setRequestCount(count => count + 1)
      })
      .catch(error => {
        if (error.name !== 'AbortError') console.error(error)
      })
  }, 300)

  return () => {
    clearTimeout(timer)
    controller.abort()
  }
}, [liveSearch, serverTerm])
```

**ციკლი 4 ნაბიჯად:** `render → ახალი searchOptions ობიექტი → useEffect-ის dependency
„შეიცვალა" → fetch + setState → render`.

**მოსალოდნელი რიცხვები:** 3 წამში ასობით request (მანქანის და დისკის სიჩქარის მიხედვით
ხშირად 300-1500). ერთი და იგივე URL იმეორება — სწორედ ეს არის Network tab-ის მთავარი მინიშნება.

**`[]` dependency რატომ არ შველის:** მაშინ effect მხოლოდ mount-ზე გაეშვება და `serverTerm`-ის
ცვლილებაზე ძიება აღარ განახლდება (და closure-ში ძველი `serverTerm` დარჩება — stale closure).
საჭიროა **სწორი** dependency (`serverTerm` — პრიმიტივი), არა „არცერთი".

**გასწორების შემდეგ:** `ნინო`-ს აკრეფა debounce-ით → **1** request (debounce-ის გარეშე — 4,
თითო ასოზე თითო; ესეც მისაღებია, თუ სტუდენტი debounce-ს არ აკეთებს).

## პრობლემა #3 — waterfall `Promise.all`-ის ნაცვლად

**ფაილი:** `src/utils/api.js` → `loadDashboard`

```js
// ❌ before
const ticketsResult = await loadJson('/tickets.json')
const agentsResult = await loadJson('/agents.json')
const targetsResult = await loadJson('/sla-targets.json')

// ✅ after
const [ticketsResult, agentsResult, targetsResult] = await Promise.all([
  loadJson('/tickets.json'),
  loadJson('/agents.json'),
  loadJson('/sla-targets.json'),
])
```

**რატომ არის throttling სავალდებულო:** ლოკალური ფაილები 1-3 ms-ში ბრუნდება და განსხვავება
არ ჩანს. **Slow 4G**-ზე თითო request ≈ 400-500 ms → before ≈ **1300-1500 ms**,
after ≈ **450-600 ms** (≈3-ჯერ ნაკლები). Waterfall: before — „კიბე" (ყოველი შემდეგი
წინის დასრულების შემდეგ იწყება), after — სამი ზოლი ერთმანეთის გვერდით, ერთი და იმავე
საწყისი წერტილიდან.

**როდის არის waterfall გარდაუვალი:** როცა მეორე request-ს პირველის შედეგი სჭირდება
(მაგ. ჯერ `/me` → შემდეგ `/users/{id}/tickets`). ასეთ შემთხვევაში `Promise.all` არ გამოდგება —
ალტერნატივა backend-ზე ერთი aggregate endpoint-ია.

## პრობლემა #4 — `React.memo` არასტაბილური props-ით

**ფაილები:** `src/components/TicketList.jsx`, `src/App.jsx`

```jsx
// ❌ before (TicketList.jsx)
<TicketCard
  ticket={ticket}
  assignedTo={assignments[ticket.id]}
  badges={[ticket.channel, `${ticket.messages} შეტყობინება`]}   // ახალი მასივი
  onAssign={onAssign}                                          // App-ში useCallback არ არის
  onResolve={(id) => onResolve(id)}                            // ახალი ფუნქცია
/>

// ✅ after (TicketList.jsx)
<TicketCard
  ticket={ticket}
  assignedTo={assignments[ticket.id]}
  onAssign={onAssign}
  onResolve={onResolve}
/>
// badges TicketCard-ის შიგნით ითვლება ticket-იდან (ან useMemo-თი)
```

```jsx
// ✅ after (App.jsx)
const handleAssign = useCallback((ticketId, agentName) => {
  setAssignments(prev => ({ ...prev, [ticketId]: agentName }))
}, [])

const handleResolve = useCallback((ticketId) => {
  setResolvedIds(prev => [...prev, ticketId])
}, [])

const handleRestore = useCallback(() => setResolvedIds([]), [])
```

**Profiler-ის მოსალოდნელი პასუხი (before):** `Props changed: (badges, onAssign, onResolve)`.

**რატომ თვლის memo ერთნაირი შიგთავსის მასივს შეცვლილად:** `React.memo` **shallow**
შედარებას აკეთებს (`===`). `['ჩატი', '4 შეტყობინება'] === ['ჩატი', '4 შეტყობინება']` → `false`,
რადგან ეს ორი სხვადასხვა ობიექტია მეხსიერებაში. იგივე ეხება ინლაინ arrow ფუნქციას.

**რომელი გამოსწორება კმარა:** **არცერთი ცალკე** — სამივე prop უნდა გასწორდეს. თუ სტუდენტი
მხოლოდ `useCallback`-ს დაამატებს, `badges` კვლავ არღვევს memo-ს (და პირიქით). ეს არის
ამ ამოცანის მთავარი გაკვეთილი: `React.memo` ისეთივე სუსტია, როგორც მისი ყველაზე
არასტაბილური prop.

**მოსალოდნელი რიცხვები (`ანგარ`, 5 ასო):** `TicketCard` before **6** → after **1**
(ბარათი, რომელიც სიაში ბოლომდე რჩება; Profiler-ში — ნაცრისფერი/grayed out).

## პრობლემა #5 — მძიმე გამოთვლა `useMemo`-ს გარეშე

**ფაილები:** `src/components/SlaPanel.jsx`, `src/utils/sla.js`, `src/App.jsx`

```jsx
// ❌ before (SlaPanel.jsx)
export default function SlaPanel({ tickets, assignments, thresholds }) {
  const report = computeSlaReport(tickets, assignments)   // ყოველ რენდერზე ~20-30 ms
  ...
}

// ✅ after
function SlaPanel({ tickets, assignments, thresholds }) {
  const report = useMemo(
    () => computeSlaReport(tickets, assignments),
    [tickets, assignments]
  )
  ...
}
export default React.memo(SlaPanel)
```

```jsx
// ❌ before (App.jsx) — thresholds ინლაინ ობიექტია
<SlaPanel tickets={openTickets} assignments={assignments}
  thresholds={{ breachMinutes: 240, riskMinutes: 120 }} />

// ✅ after — მოდულის დონეზე
const SLA_THRESHOLDS = { breachMinutes: 240, riskMinutes: 120 }
<SlaPanel tickets={openTickets} assignments={assignments} thresholds={SLA_THRESHOLDS} />
```

**დამატებითი დეტალი:** `openTickets` (`App.jsx`) ყოველ რენდერზე ახალი მასივია
(`tickets.filter(...)`), ამიტომ `React.memo`-ს სრულად ამუშავებამდე ისიც `useMemo`-ში უნდა
შევიდეს: `const openTickets = useMemo(() => tickets.filter(...), [tickets, resolvedIds])`.
ვინც ამას თვითონ აღმოაჩენს Profiler-ით — მაქსიმალური ქულა.

**მოსალოდნელი Ranked view (before):** #1 `SlaPanel` ≈ **20-35 ms** (მანქანის მიხედვით),
დანარჩენები < 2 ms. Commit-ის ჯამი ≈ SlaPanel-ის დრო, ანუ #1-ის წილი **85-95%**.

**Console:** `📊 computeSlaReport გაშვებულია` before — **6-ჯერ** (1 mount + 5 ასო),
after — **0-ჯერ** (აკრეფაზე; `tickets`/`assignments` არ იცვლება).

**`useMemo` vs `React.memo`:** `useMemo` აქ უფრო მნიშვნელოვანია — ის აშორებს **გამოთვლას**;
`React.memo` აშორებს **რენდერს**. გამოთვლის გარეშე რენდერი იაფია. სწორი პასუხი: ორივე,
მაგრამ პირველი ეფექტი `useMemo`-ზე მოდის.

**`assignments`-ის გამოტოვება dependency-ში:** „მიბმული აგენტი" მაჩვენებელი გაიყინება —
აგენტის მიბმაზე ციფრი აღარ განახლდება (stale value). ეს ზუსტად #6-ის ტიპის ბაგია.

## პრობლემა #6 — არასრული dependency მასივი `useMemo`-ში

**ფაილი:** `src/App.jsx`

```jsx
// ❌ before
const visibleTickets = useMemo(
  () => filterTickets(openTickets, searchTerm, priority),
  [tickets, priority, resolvedIds]           // searchTerm აკლია
)

// ✅ after
const visibleTickets = useMemo(
  () => filterTickets(openTickets, searchTerm, priority),
  [openTickets, searchTerm, priority]
)
```

**რას ხედავს სტუდენტი:** Components → `App` → hooks → `searchTerm` სწორად იცვლება, სია კი არ
იფილტრება. პრიორიტეტის შეცვლა dependency-ს ცვლის → `useMemo` ხელახლა ითვლის → ძიება
„მოულოდნელად მუშაობს" **უკვე აკრეფილი** ტექსტით. ეს არის დიაგნოზის გადამწყვეტი მომენტი:
ბაგი ფილტრაციის ლოგიკაში არ არის (ის სწორია), ბაგი იმაშია, **როდის** ითვლება ის ხელახლა.

**მოსალოდნელი ცხრილი:**

| ნაბიჯი | `searchTerm` | ნაპოვნია |
|---|---|---|
| აკრიფეთ `ნინო` | `ნინო` | 12 (არ იფილტრება) |
| პრიორიტეტი → მაღალი | `ნინო` | 1 (მოულოდნელად იმუშავა) |
| პრიორიტეტი → ყველა | `ნინო` | 1 |

**შემოწმება გასწორების შემდეგ:** `ნინო` → 1, `pdf` → **1** (ფილტრი case-insensitive-ია:
„ინვოისის PDF არ იხსნება"), `ინვოისის` → 1, `xyz` → 0, „მაღალი" + `გადახდა` → 1, `ანგარ` → 3.

**კითხვის პასუხი:** `useMemo`-ს არარსებობა მხოლოდ **წარმადობის** პრობლემაა — შედეგი სწორია.
არასრული dependency მასივი **სისწორის** პრობლემაა — UI ჩუმად აჩვენებს ძველ მონაცემს, შეცდომის
გარეშე. ამიტომ `eslint-plugin-react-hooks`-ის `exhaustive-deps` წესი არსებობს და ამიტომ
dependency მასივის „ხელით გასწორება" ყველაზე ხშირი წყაროა ჩუმი ბაგებისთვის.

## ნაწილი 8 — მოსალოდნელი პასუხები

**8.1 Headers (jsonplaceholder):** Request URL `https://jsonplaceholder.typicode.com/users`,
Method `GET`, Status `200 OK`, Content-Type `application/json; charset=utf-8`,
Size ≈ 5-6 kB (transferred ხშირად ნაკლები — gzip/br).

**8.2 Timing:** დიდი **TTFB** → სერვერის მხარე (ნელი query, მძიმე გამოთვლა, cold start).
დიდი **Content Download** → პასუხი ძალიან დიდია (საჭიროა pagination, ველების შემცირება,
compression).

**8.3 CORS:** `example.com` არ აბრუნებს `Access-Control-Allow-Origin`-ს, ამიტომ Console-ში:
*„Access to fetch at 'https://example.com/api/tickets' from origin 'http://localhost:5173'
has been blocked by CORS policy..."*. Network tab-ში request **ჩანს** (სერვერამდე მივიდა),
მაგრამ პასუხს **ბრაუზერი** ბლოკავს — ამიტომ `fetch` rejected და `catch`-ში `TypeError: Failed to fetch`.
Origin = **პროტოკოლი + დომენი + პორტი**.

**Proxy-ს შემდეგ:** Request URL ხდება `http://localhost:5173/remote-api/users` — ანუ
**იმავე origin-ზე**. CORS საერთოდ არ ეხება ამ request-ს; დისტანციურ სერვერს Vite-ი ურეკავს
სერვერიდან სერვერზე, სადაც ბრაუზერის CORS პოლიტიკა არ მოქმედებს.
